## 2026-09-29 타일 워크스페이스 서브 타일은 iframe [일부 대체 → 2026-10-01 타일 큐: 왼쪽 칸 고정·새로고침 소실 부분]

- 이유: App Router 페이지가 Server Component일 수 있어 클라이언트에서 임의로 동적 import해 그릴 수 없다. iframe이면 서버 렌더링·데이터 fetch·인증 쿠키(same-origin)가 그대로 동작하고 Next.js 라우팅 내부를 우회할 필요가 없다. 대안(세 경로를 주소창 쿼리에 인코딩해 새로고침에도 복원)은 라우트 조회 테이블 등 인프라가 커서, 아직 listing/chat 도메인 페이지 자체가 없는 지금 시점엔 과함.
- 따라오는 제약: 서버가 나중에 X-Frame-Options/CSP frame-ancestors를 설정하면 same-origin(`'self'`)은 허용해야 한다 (`docs/security.md` 참고). `<iframe onError>`는 HTTP 레벨 실패(404/500)엔 안 믿음직하게 발동하는 브라우저 표준 한계 — 필요해지면 postMessage 핸드셰이크로 보완.
- 재검토 조건: 서브 타일 공유 링크(새로고침 후 3분할 복원)가 실제로 필요해질 때. 스펙: `docs/superpowers/specs/2026-09-29-tile-workspace-design.md`.

## 2026-10-01 화면 전환은 전부 타일 큐 엔진 (화면별 분할 금지) [일부 대체 → 2026-10-19 홈 고정·주기능·보조: 큐·리셋 부분]

- 결정: 화면 전환은 특정 화면마다 처리하지 않고 전부 타일 워크스페이스 엔진 하나를 탄다 (사용자 지시). 전체 → (연관 화면 열기) 1/2 | 1/2 → 1/2 | 1/4·1/4. 가득 차면 가장 오래된 칸(왼쪽)이 빠지고 한 칸씩 당겨진다(진짜 큐). 연관 없는 화면을 열면 리셋(새 전체화면). 연관 여부는 화면별 그룹 표 하나로 판단하고, 표에 없는 화면은 연관 없음(리셋). 공통 그룹(홈·로그인·가입 등)은 어느 칸과도 연관. 헤더 로고는 항상 리셋, 나머지 헤더 링크는 같은 규칙. 모든 칸에 닫기, 왼쪽 칸을 닫으면 다음 칸이 주소창 칸으로 올라온다. 새로고침해도 칸 구성 그대로 복원.
- 이유: 화면마다 분할을 따로 만들면(검색 `SearchSplitShell`, 로그인 `AuthSplitShell`) 동작이 화면마다 달라지고 새 화면마다 또 만들어야 한다. 판매·구매 같은 예는 예시일 뿐 규칙은 모든 화면에 같다.
- 바뀌는 것: 09-29 타일 워크스페이스의 "왼쪽 칸 고정, 오른쪽 두 칸만 FIFO"와 "새로고침 시 서브 타일 소실"을 대체. 로그인·가입 전용 3분할(`AuthSplitShell`의 위 칸 쌓기)도 엔진으로 옮긴다. 구현은 `feat/tile-queue`.
- 재검토 조건: 칸 4개 이상이 필요해질 때, 모바일에서도 분할이 필요해질 때.

## 2026-10-02 파일 저장소는 서버 로컬 디스크, 2단계 업로드

- 결정: 업로드 파일은 서버 디스크(Docker volume `uploads_data`, api-1·api-2 공유)에 저장한다. MinIO 안 씀. 폴더는 `public|private/도메인/종류/yyyy/MM/<uuid>.<ext>`, DB엔 키만. 파일을 먼저 올려(`POST /api/v1/uploads`) 키를 받고 매물 등록·수정에 키를 넣는 2단계 — 본인이 24시간 안에 올린 키만 받는다(Redis 기록). 사진은 공개, 데이터시트·테스트리포트·정품인증서·대체품은 로그인 사용자만 열람 (사용자 지시).
- 이유: 서버 1대라 MinIO의 장점(여러 서버 공유, S3 API, 서명 URL)이 필요 없고 컨테이너만 늘어난다(09-28 이미지 문제 이력). `FileStorage` 인터페이스 뒤라 구현만 바꾸면 교체된다. 2단계는 기존 JSON 등록 API를 그대로 두고 PATCH도 같은 업로드를 쓴다.
- 대안: MinIO, 등록 요청을 multipart 한 번으로 — 기존 API 변경·실패 시 전부 재전송이라 탈락.
- 감수: 올리고 등록 안 한 고아 파일이 남는다(당분간 수동 정리). volume은 DB와 함께 백업 대상. 스펙: `docs/superpowers/specs/2026-10-02-file-upload-design.md`.
- 용량 한도 (리뷰 후 추가): 사용자당 하루 300MB + 디스크 여유 10GB 미만이면 거부. 횟수 한도(20회/10분)만으로는 계정 하나가 하루 약 29GB를 채울 수 있고, 디스크가 차면 같은 디스크의 Postgres까지 멈춘다. 개수 한도는 10MB 파일이면 무의미해 바이트로. 수정(PATCH) 시 파일 칸 `""` = 비우기 — Java에서 null과 생략을 구분하는 것(JSON Merge Patch)보다 단순해서.
- 재검토 조건: 서버 2대 이상, 대용량 직접 업로드(서명 URL)·CDN이 필요할 때.

## 2026-10-02 매물 상세: 클라이언트 조회, 비공개 PDF는 blob으로 받아 iframe

- 결정: `/listings/{userId}/{regDate}`는 클라이언트 컴포넌트가 `lib/api/client.ts`로 매물과 `me()`를 동시에 조회한다. 데이터시트 PDF·서류는 `fetchFile`로 Blob을 받아 `blob:` URL을 iframe·새 탭에 띄운다.
- 이유: `client.ts`가 유일한 백엔드 호출 지점이고 refresh가 이미 있다. 판매자 버튼 판단과 PDF는 어차피 브라우저 몫. API 주소를 iframe에 직접 넣으면 Spring Security 기본 `X-Frame-Options: DENY`에 막히고, access 토큰(15분) 만료 시 iframe은 refresh를 못 한다.
- 대안: 서버 컴포넌트 fetch(첫 화면에 내용이 차고 검색엔진이 읽음) — 서버→API 호출 경로가 새로 생겨 탈락. 파일 API의 frame 헤더 완화 — 보안 헤더를 바꾸고도 토큰 만료 문제가 남아 탈락.
- 재검토 조건: 매물 페이지의 검색 노출·링크 미리보기가 필요해질 때(페이지 껍데기만 서버 조회로). 스펙: `docs/superpowers/specs/2026-10-02-listing-detail-design.md`.
- 사진·데이터시트는 그 매물에 올린 것만 보인다. 없으면 없는 대로 (사용자 결정, 코드리뷰 후). 처음 스펙은 상품마스터의 `prod_photo_1`·`prod_data_sheet`로 대신했지만, 이 값은 같은 상품명+제조사를 처음 등록한 다른 판매자의 실물 사진·파일이라 구매자가 다른 물건을 보고 판단하게 된다. 상세 응답에서도 두 키를 뺐다.

## 2026-10-02 매물 검색: 기존 목록 API에 필터·커서 [더 보기], 카테고리 필터 보류 [일부 대체 → 2026-10-19 카테고리·상세 필터]

- 결정: 새 경로 없이 `GET /api/v1/listings`에 `q`·`field`·`status`·재고·가격·납품일과 `total`을 붙인다. 커서 페이지네이션 + [더 보기] (사용자 확인). 검색 결과 화면은 클라이언트 조회, mock·프론트 필터 함수 삭제.
- 카테고리 필터는 뺀다 (사용자 결정): 화면 카테고리(한글 이름)와 `category_code`(자유 코드, `prod_id` 앞 8자리)가 안 맞고 카테고리 마스터가 미정. 골라도 안 바뀌는 select는 고장으로 보여 홈 검색창·필터 바에서 숨겼다.
- 이유: 리소스 목록 + 쿼리 파라미터가 규칙(`backend.md`)이고 이미 공개 조회라 보안 설정이 안 바뀐다. 커서는 보는 중 새 매물이 등록돼도 중복·누락이 없다.
- 쿼리는 동적 JPQL(`ListingSearchRepository`) — security.md "문자열 결합 쿼리 금지"의 예외로 둔다. 코드에 고정된 조건 조각만 잇고 값은 전부 바인딩한다. Criteria API·Specification은 같은 안전성에 코드가 2~3배라 탈락. 사용자 입력이 조각 선택(정렬 필드 등)에 쓰이게 되면 허용 목록 switch로만 고르고, 그게 늘면 Criteria로 옮긴다.
- 대안: 별도 `/listings/search` 경로(permitAll 추가 필요), offset 페이지 번호(`backend.md` 금지), 카테고리 코드↔이름 프론트 상수·마스터 테이블(마스터 결정과 같이).
- 재검토 조건: 카테고리 마스터가 정해질 때(select 복원), 검색이 느린 게 측정될 때(pg_trgm 등). 스펙: `docs/superpowers/specs/2026-10-02-search-api-design.md`.

## 2026-10-02 매물 등록 폼: 거래종류 "판매" 고정(임시) [거래종류 부분 대체 → 아래 거래종류 "등록"], 상품상태 형식, 날짜 범위

- 결정: `/listings/new` 직접 입력 폼은 거래종류를 화면에 두지 않고 `"판매"`로 보낸다(값 목록이 정해지면 수정, 사용자 지시). 상품상태는 `신품` 또는 `신품대비 N%`(1~99)만, 제조일은 `yyyyMMdd`·오늘까지, 납기일은 `YYYY-MM-DD`·오늘부터 — 프론트·백엔드 같은 규칙. 카테고리는 코드 체계가 미정(아래 "미정")이라 임시 텍스트 칸.
- 이유: 상태를 자유 텍스트로 받으면 "S급"·"거의 새것"처럼 제각각 쌓여 필터를 못 붙인다. 레거시 설명이 "신품대비 00%". "오늘"은 한국 날짜 — 서버 Clock이 UTC라 그대로면 한국 오전 9시 전에 오늘 납기가 거부된다.
- 감수: 옛 개발 데이터(`new`, `등록`)는 그대로 남고 새 쓰기만 검사한다. 임시 카테고리 값은 마스터 도입 때 정리.
- 재검토 조건: 거래종류 값 목록 확정, 카테고리 마스터 도입, 상태에 등급(S/A/B) 같은 다른 체계가 필요할 때. 스펙: `docs/superpowers/specs/2026-10-02-listing-create-design.md`.

## 2026-10-02 거래종류는 "등록" 고정

- 결정: 등록 폼이 보내는 거래종류를 `"판매"`에서 `"등록"`으로 바꾸고, 임시가 아니라 고정이다 (사용자 결정). 화면에는 여전히 칸이 없다.
- 이유: 레거시 컬럼 설명도 "거래종류 (등록)"이다 (data-model.md). 값 목록을 따로 정할 필요가 없어졌다.
- 감수: PR #29~이번 사이에 개발 DB에 "판매"로 들어간 행은 그대로 둔다(운영 데이터 없음). 백엔드는 여전히 20자 이하 자유 텍스트로 받는다 — 수정(PATCH)·레거시 값과 맞추려고 값을 강제하지 않는다.
- 재검토 조건: 구매 요청 등 다른 거래종류가 생길 때.

## 2026-10-06 상품상태는 드롭다운 구간, 등록 폼 라벨은 왼쪽

- 결정: 상품상태를 "신품 / 중고 + 신품대비 N%" 직접 입력 대신 드롭다운 구간으로 받는다 — `신품`, `신품대비 90~99%`, `80~89%`, `70~79%`, `60~69%`, `50~59%`, `신품대비 50% 미만`. 저장 값 = 보이는 값. 프론트 `PROD_STATES`와 백엔드 `PROD_STATE_PATTERN`이 같은 목록. 등록 폼 라벨은 입력 왼쪽, 짧은 칸은 한 줄에 둘 (사용자 지시).
- 이유: 숫자를 직접 치면 같은 상태가 70%·72%·75%처럼 흩어져 비교·필터가 어렵다(사용자 지시). 구간 폭은 사용자가 맡김 — 100%와 80%대를 한 구간으로 묶으면 차이가 너무 커서 위쪽을 10% 단위로, 50% 아래는 거래가 드물어 하나로.
- 감수: 이전 형식(`신품대비 70%`)으로 저장된 개발 데이터는 그대로 보이지만, 그 값으로 PATCH 하면 400이다. 수정 화면을 만들 때 옛 값은 가까운 구간으로 바꿔 보여 준다.
- 대안: 위쪽을 더 촘촘히(99~95/94~90) — 사용자가 10% 단위를 골랐다.
- 재검토 조건: 등급(S/A/B) 체계가 필요할 때, 구간별 검색 필터를 붙일 때. 2026-10-02 매물 등록 폼의 상품상태 형식 부분을 대체한다.

## 2026-10-06 매물 수정·판매정보 추가등록: 화면 분리, 바뀐 칸만 PATCH, 보증은 개월 드롭다운

- 결정: 수정(`/listings/{userId}/{regDate}/edit`)과 판매정보 추가등록(`/listings/extra` 고르기 → `/listings/{userId}/{regDate}/extra` 입력)을 화면 따로 만든다 (사용자 지시: 홈의 추가등록 아이콘은 수정 폼이 아니라 추가등록으로). 저장은 처음 값과 달라진 칸만 `PATCH`로 보내고 지운 칸은 `""`. 보증기간은 개월 드롭다운(없음·1·3·6·12·24·36개월)이고 서버는 같은 일수 목록(0·30·90·180·360·720·1080)만 받는다. 내 매물 고르기용 `GET /api/v1/listings/mine`을 추가한다.
- 이유: 한 화면에 합치면 같은 매물을 두 곳에서 고치게 되지만, 사용자가 용도가 다른 두 흐름으로 정했다. 바뀐 칸만 보내면 옛 형식 값(상품상태 `신품대비 70%`·보증 365일)을 사용자가 안 건드렸을 때 서버에 다시 보내 400이 나는 일이 없다. 자유 숫자 보증기간은 365·360처럼 같은 뜻이 흩어진다(상품상태 구간과 같은 이유).
- 감수: 옛 형식 상태 값은 수정 화면에서 가까운 구간으로 보여 주므로 저장하지 않는 한 DB 값은 그대로다. 옛 보증 일수(365)는 건드리지 않으면 그대로 두고, 건드리면 목록 값만 쓸 수 있다.
- 대안: 한 화면에 "기본 정보"와 "판매정보" 구역을 두기 — 사용자가 따로를 골랐다.
- 재검토 조건: 보증·불량지원 짝 검증이 필요해질 때, 판매정보 값 이력이 필요해질 때. 스펙: `docs/superpowers/specs/2026-10-06-listing-edit-extra-design.md`.

## 2026-10-06 헤더 사용자 메뉴와 마이페이지, 내 판매글은 마이페이지 안 [일부 대체 → 2026-10-06 내 판매글은 검색형 화면]

- 결정: 로그인 후 헤더의 "닉네임님 + 로그아웃"을 닉네임 첫 글자 원(사업자는 진한 면 + 흰 테두리) 하나로 바꾸고, 누르면 메뉴(맨 위 닉네임 + 개인/사업자 배지, [마이페이지], [로그아웃])가 열린다. 마이페이지(`/my`)는 사용자 카드 + 내 판매글 목록이다. `/mine` 응답에 단가·수량·거래상태·대표 사진 키를 더했다.
- 이유: 내 판매글은 "새로 하는 동작"이 아니라 목록 관리라 홈 판매 아이콘 줄(동작 바로가기, 모바일 한 줄)보다 "내 것"이 모이는 마이페이지가 맞다. 메뉴는 갈 화면이 있는 항목만 둔다 — 설정·내 정보 관리는 화면이 생길 때 추가. 당근식 프로필(매너온도·후기)은 평가 체계가 없어 개인/사업자 배지로 대신한다. 이메일·전화·실명은 메뉴·카드에 넣지 않는다(개인정보).
- 대안: 홈 판매 아이콘에 "내 판매글" 추가 — 줄이 넘치고 성격이 달라 탈락. 별도 `/my/listings` — 마이페이지에 목록 하나뿐이라 지금은 `/my`가 곧 그 화면.

## 2026-10-06 내 판매글은 검색 결과 화면 모양 + 행 안 수정, 마이페이지는 허브

- 결정: 사용자 메뉴는 마이페이지 · 내 판매글 · 내 구매목록 · 로그아웃. `/my`는 사용자 카드 + 바로가기 허브, `/my/listings`는 검색 결과 화면(`/search`)과 같은 부품(검색창·필터·표/카드·[더 보기])에 `scope="mine"`을 넘긴 화면(체크·견적·구매 없음, 거래상태 기본값 "전체"), `/my/purchases`는 구매 기능이 없어 빈 화면. 표의 행 끝 [수정]은 그 행만 맨 위에 남기고 상품명·번호·제조사·제조일·상품상태·보증기간·불량지원을 그 자리 입력칸으로, 상품설명·데이터시트·사진·대체품·테스트리포트·정품인증서는 행 아래 폼으로 고친다. 저장은 [저장] 한 번(바뀐 칸만 PATCH). 서버: 검색 `mine=true`(로그인 필수, 본인 id 는 인증 정보에서만), PATCH 에 상품 칸.
- 상품 칸 규칙: 상품마스터는 (이름, 제조사)가 유일하고 다른 판매자 매물과 공유한다. 이름·제조사가 바뀌면 `findOrCreate`로 그 상품을 찾아 이 매물만 옮긴다(없으면 새로 만든다). 그대로이고 번호·제조일 등만 바뀌면 이 매물만 쓰는 상품일 때만 고치고, 공유 중이면 422 `PRODUCT_SHARED`. 상품마스터 목록에서 고르기는 상품마스터가 다 만들어진 뒤로 미룬다(사용자 지시) — 그때 "이름·제조사 자유 입력"을 "목록에서 고르기"로 바꾼다.
- 이유: 판매글이 많아지면 단순 목록으로는 찾기 어렵다(사용자). 검색 부품을 재사용하면 필터·커서·빈 상태·오류 처리가 그대로 따라온다. 상품 칸을 그대로 고치게 하면 남의 매물이 바뀌므로 이 매물만 옮기거나 막는다.
- 감수: 표에 없는 칸(단가·판매수량·재고·최소주문·주문단위·납기일)은 행 안에서 못 고치고 상세의 [수정] 화면에서 고친다(표를 검색과 똑같이 두라는 지시). 좁은 카드(칸 폭 576 미만)는 행 안 수정 대신 [수정]이 기존 수정 화면으로 간다. 상품명을 바꾸면 이름이 같은 다른 상품으로 연결될 수 있다(자유 입력이라 비슷한 이름이 늘어날 수 있음 — 상품마스터 고르기로 해결 예정).
- 대안: `/my`에 단순 목록 — 많아지면 못 찾아 탈락(이 항목이 대체). 허브 없이 `/my/listings`만 — 메뉴가 "마이페이지"를 가리킬 곳이 필요해 탈락.
- 재검토 조건: 상품마스터가 다 만들어졌을 때(고르기로 교체), 구매 기능이 생겼을 때(내 구매목록 채움), 표에 없는 칸도 행 안에서 고쳐야 할 때. 스펙: `docs/superpowers/specs/2026-10-06-my-listings-design.md`.

## 2026-10-06 개발 서버를 localhost 와 다른 주소로 함께 쓴다 — 주소는 .env, API 는 같은 주소의 /api

- 결정: VM 에 `pnpm dev` 를 띄우고 다른 PC 에서 사설 IP 로 들어가도 localhost 와 같이 동작하게 한다. 실제 주소·IP 는 코드·문서·커밋에 쓰지 않고 `.env`(백엔드)·`frontend/.env.local`(프론트)에만 둔다(사용자 지시). 프론트: `NEXT_PUBLIC_API_URL=same-origin`(또는 빈 값)이면 브라우저는 접속한 주소의 `/api` 만 부르고 `next.config.ts` 의 rewrites 가 `API_PROXY_TARGET`(기본 localhost:8080)으로 넘긴다. `DEV_ALLOWED_ORIGINS`(쉼표, 호스트 이름만)로 Next 개발 서버의 cross-origin 차단을 푼다. 백엔드: `ALLOWED_ORIGINS`(쉼표 목록)로 허용 출처를 APP_URL 에 더하고, `COOKIE_SECURE=false` 로 http 에서 쿠키가 저장되게 한다 — 둘 다 기본값은 지금과 같고(`COOKIE_SECURE` 는 `APP_ENV=local` 이 아니면 false 로 기동 못 함).
- 이유: 설정이 없으면 (1) Next 16 개발 서버가 localhost 밖에서 오는 JS 요청을 403 으로 막아 화면이 안 눌리고(재현: Origin 이 localhost 면 200, 사설 IP 면 403) (2) 브라우저의 localhost:8080 은 접속하는 PC 자신이라 API 에 못 닿고 (3) Secure 쿠키는 http 사설 IP 에서 저장되지 않아 로그인이 유지되지 않는다. 같은 주소의 /api 로 부르면 접속 주소가 바뀌어도 API 주소를 따로 맞출 필요가 없고 CORS 도 거치지 않는다.
- 감수: `ALLOWED_ORIGINS` 를 운영에 두면 CSRF 방어(Origin 검사)가 넓어지므로 운영 `.env` 에는 두지 않는다(와일드카드 없음, 목록만). 개발 서버를 거치는 프록시라 큰 업로드(10MB)는 개발 서버 한도에 걸릴 수 있다 — 안 되면 `NEXT_PUBLIC_API_URL` 에 직접 주소를 쓴다.
- 대안: IP 를 next.config·application.yml 에 박기 — 커밋에 개인 IP 가 남아 탈락(사용자 지적). API 주소를 접속 호스트로 계산(`hostname:8080`) — 백엔드 포트도 열어야 하고 CORS 가 필요해 탈락.
- 재검토 조건: 스테이징·운영에 올릴 때(https·실제 도메인이면 이 설정은 필요 없음), 업로드가 개발 프록시에서 막힐 때.

- 구현 선택: 재고 차감·상태 변경은 조건부 UPDATE 한 문장(락 없이 음수·이중 확정 방지). 거래ID 순번은 시간대별 advisory lock(Postgres 는 실패한 문장 뒤 같은 트랜잭션에서 재시도 불가). 요청 건수는 매물 검색 응답이 아니라 `GET /api/v1/trades/pending-counts` — 매물 → 거래 역참조(순환 의존)를 피하려고. 매물 삭제의 "거래 있음"도 FK 위반을 409 로 바꿔 매물 쪽이 거래 테이블을 보지 않는다.
- 범위 밖: 장바구니·비교용, 견적, 자동 확정·기간 제한 취소(사용자가 나중에 정함), 공통코드 테이블, 결제·배송, 취소한 사람 기록.
- 재검토 조건: 견적 흐름을 정할 때(판매자 승인·단가 조정), 자동 확정·취소 기한을 정할 때(요청일시 칸·스케줄러 필요), 숫자 코드로 바꿀 때. 스펙: `docs/superpowers/specs/2026-10-15-purchase-design.md`.

- 감수: 넓은 화면에선 홈 iframe 을 늘 하나 더 불러온다(가벼운 화면이라 감수). 주기능은 오른쪽 위 칸이라 보조가 열리면 화면의 1/4 이다(기존 3분할 배치 그대로).
- 재검토 조건: 주기능 칸을 더 넓게(예: 홈을 좁게) 바꾸고 싶을 때, 모바일 분할이 필요할 때.

## 2026-10-19 검색 화면 맨 위 [전체 / 내 판매] 범위 전환

- 결정 (사용자 지시): `/search` 맨 위에 [전체 | 내 판매] 두 칸을 둔다. 내 판매는 같은 검색 화면에서 내 글만 거른다(`?mine=1` → API `mine=true`). 내 판매글 화면(`/my/listings`)에는 넣지 않는다(사용자 선택 — 거긴 늘 내 글).
- 구현 선택: 범위는 필터 바가 아니라 별도 링크 두 개라 [적용] 없이 바로 바뀌고, 검색어·필터는 그대로 남는다. 필터 개수에 세지 않고 [초기화]해도 유지. 거래상태 기본값은 검색 그대로(거래 가능). 내 판매는 `RequireLogin` 으로 감싸 비로그인이면 로그인 화면 — 서버도 `mine=true` 비로그인을 401 로 막는다. 결과 표는 검색 모양 그대로(체크·견적·구매 있음, [수정] 없음).
- 감수: `RequireLogin` 의 돌아올 경로가 pathname 만이라 로그인 뒤엔 `/search`(전체)로 돌아온다.
- 대안: 검색·내 판매글 둘 다 같은 전환을 두고 서로 다른 주소로 이동 — 사용자가 검색에만으로 골랐다.
- 재검토 조건: 내 판매 결과에서 [수정]·구매요청 건수가 필요할 때(그땐 내 판매글 화면과 합칠지 다시).

## 2026-10-19 검색 필터: 카테고리 복원 + [상세 필터] 7개

- 결정 (사용자 지시 "넣어도 되는 거 싹 다", 배치는 상세 필터로 나눔): 늘 보이는 줄은 거래상태 · 카테고리 · 재고 · 가격. [상세 필터]를 펼치면 납품일 · 상품상태(그 구간 이상) · 제조사(부분 일치) · 보증기간(N개월 이상) · 불량지원(대체·환불) · 자료 있음(데이터시트·사진·테스트리포트·정품인증서·대체품, 고른 것 전부) · 최소주문(N개 이하로 살 수 있는 것). 검색·내 판매글이 같은 필터 바라 둘 다 생긴다.
- 이유: 10-02 에 카테고리를 뺀 이유(마스터 미정)는 10-13 카테고리 마스터 도입으로 사라졌다. 나머지는 매물 컬럼에 이미 있는 값이라 조건만 붙이면 된다. 11칸을 한 줄에 두면 2~3줄이 되어 결과가 밀린다.
- 구현 선택: 카테고리는 대·중·소 어디서 멈춰도 그 분류와 아래 전부(`code = :c or code like :c || '-%'`). 패널은 등록 폼과 같은 3열이지만 대·중을 눌러도 값이 된다. 상품상태는 등록 목록 순서로 "이상" — 목록 밖 옛 값(신품대비 70% 등)은 어느 구간에도 안 걸린다. 자료·사진은 검색 결과 표시처럼 매물 값만 본다(상품마스터 파일 제외). 불량지원은 URL 에 한글을 싣지 않게 영문 키. 걸린 상세 필터가 있으면 펼친 채로 열고, 상세 칸에 오류가 있으면 접어도 보인다.
- 정책 변경: `GET /api/v1/categories` 를 공개로 — 검색은 비로그인 공개인데 카테고리 패널이 이 목록을 쓴다. 분류 이름뿐이라 개인정보 없음 (security.md).
- 감수: 보증기간은 등록 선택지(1·3·6·12·24·36개월)만 고른다 — URL 에 다른 일수가 오면 버린다. 카테고리·제조사 조건에 인덱스는 없다(매물 수가 적어 측정 전엔 두지 않음).
- 재검토 조건: 상품상태를 enum 으로 바꿀 때(옛 값 이전), 검색이 느리다고 측정될 때(카테고리·제조사 인덱스), 필터가 더 늘 때(필터 패널을 옆 칸으로).
- 덧붙임 (같은 날, 사용자 지시): 필터 바를 칩 툴바로 바꿨다 — 상자 안에 칸을 늘어놓으니 줄바꿈 뒤 빈칸이 많고 [적용]·[초기화]가 칸 사이에 섞여 어색했다. 칩을 누르면 팝업. 10-01 "필터는 [적용]을 눌러야 URL 반영"은 팝업 단위로 바뀐다: 입력 칸(재고·가격·상세)은 팝업 [적용], 고르기만 하는 것(거래상태·소분류·칩 ×)은 바로. 입력 중엔 여전히 반영하지 않는다. 팝업은 shadcn Popover(`radix-ui` 패키지에 이미 있어 새 의존성 아님).

## 2026-10-20 견적요청: 희망단가 → 판매자 수락(매물 단가 변경)·거절 → 구매자가 따로 구매, 단계마다 메일

- 결정 (사용자 지시, 대화로 정함): 구매자가 검색 결과(여러 매물, 20개까지)·상세에서 [견적 요청] → 매물마다 희망단가(1 ~ 등록단가)·수량·비고. 납품희망일은 받지 않는다. 판매자가 [수락]하면 그 매물의 등록단가가 희망단가로 바뀌고(이미 더 싸면 그대로, 모든 구매자에게 적용), [거절]하면 그대로. 구매자는 바뀐 매물을 기존 [구매]로 산다(수락이 곧 구매요청은 아님). 회신 기한·자동 처리 없음.
- 거래 코드 정리: `trd_trade_info` 하나를 쓰고 TRADE_TYPE 은 "무슨 기록인가"(구매검토·견적조정·거래 — 만들 때 정하고 안 바뀜), TRADE_STATS 는 "어디까지 왔나"(장바구니·비교용·견적요청·견적회신·구매요청·구매확정 — 앞으로만). 수락·거절은 상태를 하나(`견적회신`)로 두고 어느 쪽인지는 메일로만 알린다. 취소(견적·거래 모두)는 값 없이 행을 지운다. 정의서 TYPE `요청중`은 안 씀, `견적회신`은 정의서 밖 값.
- 알림: 견적 요청·견적 취소·구매요청 → 판매자, 수락·거절 → 구매자, 거래 취소 → 상대, 거래완료 → 둘 다. 하이웍스 SMTP(`spring-boot-starter-mail`, 사용자 확인). 커밋 뒤에만 보내고 실패해도 업무는 되돌리지 않는다. 연락처는 화면·API 에 공개하지 않는다.
- 이유: 채팅 없이 단가를 맞추는 가장 단순한 길. 수락이 매물 단가를 바꾸므로 구매는 지금 흐름 그대로 재사용한다. TYPE·STATS 가 섞여 쓰이던(구매 확정·취소가 TYPE 을 바꿈) 것을 역할로 나눠, 장바구니·비교용을 더해도 같은 규칙으로 들어간다.
- 감수: 수락·거절 결과는 목록에서 구분되지 않는다(메일로만). 취소한 기록은 남지 않는다(완료된 거래는 이력 테이블에). 메일 재시도·발송 기록 없음. 기존 개발 DB 의 취소 행은 마이그레이션이 지웠다.
- 대안: 수락하면 그 단가로 바로 구매요청 — 사용자가 "매물을 바꾸고 구매는 따로"로 골랐다. 수락·거절 상태를 따로 둠 — 사용자가 하나로 충분하다고 했다. 회신 기한 — 뺐다(사용자).
- 재검토 조건: 수락/거절을 목록에서 나눠 봐야 할 때(상태 추가), 판매자가 단가를 매물 전체가 아니라 그 구매자에게만 주고 싶을 때, 메일 실패가 문제 될 때(발송 기록·재시도), 장바구니·비교용을 만들 때. 스펙: `docs/superpowers/specs/2026-10-20-quote-request-design.md`.
- 코드리뷰로 드러난 감수·미정 (2026-10-20, 사용자 결정 대기): (1) 견적 행은 회신 뒤에도 남고 지울 방법이 없어, 거래와 같이 매물 FK 가 걸려 판매자가 그 매물을 **삭제할 수 없다**(`LISTING_HAS_TRADES`). 누구나 재고·승인 없이 견적을 보낼 수 있어 악용될 수 있다 — 후보: 매물 삭제 때 견적 행을 같이 지움 / 거절이면 행 삭제 / 감수. (2) 같은 구매자가 같은 매물에 `견적요청` 을 동시에 2개 만들 수 있다(매물 잠금도 unique 제약도 없음) — 후보: `(user_id, seller_id, reg_date) where trade_stats='견적요청'` 부분 unique 인덱스(스키마 변경, `db/` 브랜치). (3) 마이그레이션 `V202610201010` 은 옛 코드와 호환되지 않는다(옛 코드는 TYPE `거래` 를 읽지 못해 거래 목록이 500). 새 코드와 **같은 배포**로만 나가야 하고, 롤백하면 지운 취소 행은 되살릴 수 없다 — 운영 데이터가 없어 이번에만 규칙(직전 배포 호환)의 예외로 둔다.

- 견적 행 정리 (2026-10-21, 사용자 결정 — 위 2026-10-20 caveat 1·2 해소): (1) 구매자·매물당 견적(견적조정) 행은 하나. 재요청은 그 행을 덮어쓰고(단가·수량·비고·매물 스냅샷) `견적요청`으로 되돌린다 — 거절·수락 뒤 재요청도 같다. 행 수가 (구매자 × 매물)로 묶여 악용 한도가 생긴다. 동시 요청은 부분 unique 인덱스 `ux_trd_trade_info_one_quote`(`db/trade-quote`)가 막고 진 쪽은 409 `QUOTE_ALREADY_REQUESTED`(재시도). (2) 거절은 행을 지우지 않는다(`견적회신` 유지) — 재활용과 겹치기 때문. (3) 매물 삭제 때 그 매물의 견적 행을 같이 지운다(`ListingDeletingEvent` → `TradeListingCleanup`, 같은 트랜잭션). 구매요청·거래 행이 있으면 기존대로 `LISTING_HAS_TRADES` 로 막는다. (4) 감수: 덮어쓴 행은 trade_id 가 그대로라 목록 최신순에서 옛 자리에 남는다. 수락이 옛 값을 읽은 직후 구매자가 덮어쓰면 옛 희망단가가 매물에 반영되고 행은 `견적요청`으로 남는다(판매자가 다시 보게 됨).

- 견적 회신을 수락·거절 두 상태로 (2026-10-21, 사용자 결정 — 2026-10-20 "견적회신 하나·결과는 메일로만"을 뒤집음): 상태가 하나면 목록에서 수락인지 거절인지 안 보이고 메일을 열어야 해 사용자가 어려워할 것 같다는 이유. `견적요청` → `견적수락`(구매자에게 [구매]만) | `견적거절`(구매자에게 [재요청]·[취소]). 둘 다 정의서 밖 값(이름은 `견적요청`에 맞춤, `V202610211100` 이 옛 `견적회신` 행을 `견적거절`로 옮김). 거절된 견적은 구매자가 취소(행 삭제)할 수 있고 판매자에게 메일은 가지 않는다(판매자가 이미 답한 건). 수락된 견적은 취소할 수 없다 — [구매]로 가거나 재요청(덮어쓰기)으로만. 재요청은 거절·수락 어느 쪽 뒤든 같은 행을 `견적요청`으로 되돌린다(위 2026-10-21 견적 행 정리). 같은 날 목록에서 거래번호(ID)를 뺐다 — 사용자에겐 의미가 없고, 견적 줄의 단가는 "희망(크게)·등록(작게)"로 나눠 보인다.

- 분할 화면 칸 사이 구분 (2026-10-21, 사용자 결정 — 타일 큐의 "칸 사이 구분은 없음(각 칸 배경)"을 뒤집음): 위아래·양옆 칸이 서로 꽉 차 경계가 안 보인다는 이유. 칸 사이 간격 8 + 바깥 여백 8(`line-2` 바탕이 비침) + 칸마다 1px `line` 테두리·모서리 10. iframe 안(framed)에는 적용하지 않으며 JS 상태가 아니라 CSS `framed:` 로 꺼서 하이드레이션 전에도 깜빡이지 않게 했다. 스펙 `2026-10-01-tile-queue-design.md` 의 같은 문구는 이 항목이 대체한다.
