## 2026-09-17 백엔드는 자체 서버(R740), 프론트는 Vercel
- 이유: 서버가 이미 있음. 월 비용 0. AI 워크로드를 서버에서 돌릴 자유. 프론트는 Vercel이 CDN·무중단을 공짜로 줌.
- 감수: 인증·배포·백업·모니터링을 직접 구현. 초기 작업량 1.5~2배.
- 대안: Supabase + Vercel 전부 클라우드. 재검토 조건: 서버 운영이 개발 시간을 잡아먹는다고 느낄 때.

## 2026-09-17 아키텍처는 모듈러 모놀리스 (+ AI 서비스 1개)
- 결정: 제품 백엔드는 프로세스 하나, DB 하나. 도메인별 패키지(`user`, `listing`, `chat`, `organization`)로 코드만 분리. controller → service → repository 3계층.
- 이유: 1인 개발. MSA는 팀 여러 개가 서로 안 밟으려는 구조이지 성능 구조가 아님. 도메인 패키지가 나중에 분리 단위가 되므로 길은 열려 있음.
- 예외: AI는 별도 Python 서비스 (아래). 그 외 서비스 분리 금지. 재검토 조건: 서버 3대 이상, 또는 팀 생김.

## 2026-09-17 배포는 Docker Compose, K8s 아님
- 이유: 서버 1대에서 K8s는 해결하는 문제가 없고 학습 비용만 큼. Compose 30줄이 K8s 300줄.
- 재검토 조건: 서버 3대 이상.

## 2026-09-17 백엔드 무중단 배포 (컨테이너 2개, 순차 교체)
- 이유: 채팅 서비스라 배포 중 끊김이 바로 체감됨. 프론트(Vercel)는 떠 있는데 백엔드만 죽으면 더 나쁘게 보임. 필요 조건(헬스체크, graceful shutdown, stateless, WS 재접속)은 어차피 있어야 하는 것들이라 추가 비용은 스크립트 10줄.
- 따라오는 규칙: DB 마이그레이션은 직전 버전 코드와 호환. 파괴적 변경은 배포 2회로 분리.
- 대안: 컨테이너 1개로 시작, 첫 유저 생기면 2개. 구조가 갖춰져 있으면 전환 30분.

## 2026-09-17 Redis는 처음부터, 조회 캐시는 나중에
- 처음부터: refresh token, WebSocket Pub/Sub, rate limit, Celery 브로커. 이것들은 Redis 아니면 둘 곳이 없고, 나중에 넣으면 WS·인증 코드를 다시 짜야 함.
- 나중에: 게시글·목록·검색 캐시. 캐시 무효화 버그가 초기 개발을 잡아먹음. 유저 적을 땐 Postgres가 1ms에 답함.
- 재검토 조건: 특정 API가 느린 게 측정되었을 때. `core/cache.py` 래퍼로만 추가.

## 2026-09-18 제품 백엔드는 Spring Boot (회사 프로젝트)
- 이유: 회사 프로젝트라 "내가 편한 언어"가 아니라 "회사 인력이 이어받을 수 있는 언어"가 기준. 한국 회사 백엔드 표준은 Spring. 인수인계·채용 모두 유리.
- 스택: Spring Boot **4.1** (뼈대 생성 시 확인: 3.5는 2026-06 OSS 지원 종료, Initializr 기본이 4.1), Java 21, Spring Security + JWT, Spring WebSocket, Flyway, JPA.
- Boot 4는 스타터 이름 등이 3.x와 달라 Claude가 틀리기 쉬움 → `rules/backend.md`에 주의 항목.
- 대안이었던 것: FastAPI 단일 백엔드. 개인 프로젝트였으면 그쪽. 재검토 조건: 없음 (회사 결정).
- 주의: `CLAUDE.md`에 Spring Boot·Java 버전을 정확히 고정. Claude가 2.x 시절 코드를 섞어 냄.

## 2026-09-18 AI는 별도 Python 서비스 (FastAPI), Spring AI 아님
- 범위: OCR + 임베딩 기반 챗봇. GPU 불필요. 엔드포인트 3개(/ocr, /embed, /chat).
- 이유: Hugging Face·PyTorch·sentence-transformers·PaddleOCR 등 AI 생태계가 Python 우선. 나중에 로컬 모델·추천·이미지 분류로 확장할 때 Java로는 막힘. Spring AI는 신생(1.0이 2025)이라 안정성·Claude 정확도 모두 낮음.
- 감수: 언어 2개, 배포 단위 2개. 완화: ai는 무상태 함수 모음으로 작게 유지, 인증·도메인 로직은 전부 Spring, HTTP 계약은 `docs/ai-api.md`에 고정.
- 경계: 외부 노출 없음(Spring만 호출), DB는 공유하되 임베딩 테이블만 접근, ai 장애 시 AI 기능만 비활성.
- 재검토 조건: GPU 추가 시 로컬 LLM 검토. AI 기능이 커지면 ai 서비스 복제(Spring과 독립).

## 2026-09-18 RabbitMQ·Celery 안 씀
- 이유: Spring으로 가면서 Celery는 해당 없음. 느린 작업(OCR·임베딩 요청)은 Spring `@Async`로 백그라운드에서 ai 호출. 부족해지면 Redis 큐.
- 재검토 조건: 작업 유실이 절대 안 되는 큐가 필요할 때 → 그때 Redis Streams 또는 RabbitMQ.

## 2026-09-17 인증: JWT access(15분, stateless) + refresh(30일, Redis)
- 이유: access는 서명 검증만으로 빠름. refresh를 Redis에 두어 로그아웃·강제 로그아웃·기기별 세션이 가능. "JWT는 로그아웃이 안 된다" 문제 해결.
- 쿠키는 루트 도메인 공유 (app./api. 같은 루트).

## 2026-09-17 외부 진입: 포트포워딩 + Cloudflare DDNS (서버는 공유기 뒤)

## 2026-09-17 리버스 프록시는 Caddy (Nginx + certbot 아님)
- 역할: HTTPS 종료, Let's Encrypt 자동 발급·갱신, api-1/api-2 로드밸런싱, 헬스체크 기반 제외, WebSocket 프록시, /media → MinIO.
- 이유: 혼자 운영이라 인증서 갱신 실패 지점을 없앰. WS·헬스체크가 설정 없이 됨. Caddyfile 10줄 vs nginx.conf 60줄 + certbot 훅.
- 주의: `caddy_data` 볼륨 필수 (없으면 재시작마다 재발급 → Let's Encrypt 주간 한도에 걸림).
- 대안: nginx + certbot. 재검토 조건: nginx 고유 기능(Lua 등)이 필요할 때. 지금 예상 없음.

## 2026-09-18 AI 기능 3개 확정
1. 견적서 PDF → 상품 등록 초안: 텍스트 추출(텍스트 PDF) 또는 OCR(스캔 PDF) → LLM 구조화 → 품목별 초안 N개 → 사용자 확인 후 게시. **자동 게시 금지.**
2. 상품 추천: 제목+스펙 임베딩 → pgvector 유사 검색. 1단계는 유사 상품, 행동 기반은 나중.
3. 챗봇 = LLM + DB 조회: tool calling으로 **미리 정의된 조회 함수만** 호출. LLM이 SQL 직접 생성 금지. 조회 함수는 Spring이 제공하고 권한 검사 통과.
   - 1단계: 함수 5~10개로 시작. 못 답한 질문은 로그로 남겨 다음 함수 목록으로.
   - 2단계: 검색 함수를 구조화 필터(JSON → 코드가 SQL 생성, 허용 테이블·컬럼 검증)로 확장.
   - Text-to-SQL(LLM이 SQL 작성)은 안 함. 재검토: 내부 관리자 전용 분석 도구에 한해.
- OCR 방식: 텍스트 PDF가 대부분이라 OCR은 스캔본 fallback. 외부 API(한글 정확도) 우선.

## 2026-09-18 API 수동 테스트 도구는 Bruno
- 요청 모음을 `bruno/` 폴더에 텍스트 파일로 저장 → git으로 diff·리뷰 가능. 외부 클라우드에 API 구조가 올라가지 않음 (회사 프로젝트).
- Swagger(Springdoc)는 "뭐 있나 보기"용으로 같이 둠. 자동 검증은 코드 테스트(`./gradlew test`)가 담당. Bruno는 손으로 확인·시나리오 재현용.
- 대안: Apidog (Springdoc 연동 편하지만 클라우드 저장·자체 형식), Postman (계정·클라우드).
- 규칙: 새 API를 추가하면 같은 PR에서 `bruno/`에 요청 파일 추가.

## 2026-09-21 계정 체계: 일반(아이디)·기업(사업자번호) 별도 계정

- 뒤집는 것: "가입은 개인만, 사업자 등록은 가입 후"(2026-09-17 판매 주체 항목) 폐기. "카카오·구글만" → 네이버 추가.
- 이유: 한국 서비스 관례(아이디 로그인, 기업 별도 가입). IT 마켓은 사업자 비중이 커서 가입 시점에 진위확인을 해야 "사업자" 뱃지가 신뢰됨.
- 감수: 기업 계정 = 담당자 1명. 담당자 퇴사 시 계정 이전은 1단계에선 고객센터 수동. `organization_members`(회사 안 여러 사용자)는 2단계.
- 재검토 조건: 기업 계정에 사용자 초대 요구가 나올 때.

## 2026-09-21 가입 흐름과 수집 정보
- 일반: 선택 → 본인인증(1단계는 UI만, PASS/NICE 계약 후 연동) → 약관 → 이름·닉네임·아이디·이메일·비밀번호·휴대폰 → 완료. 소셜 첫 로그인은 약관 + 닉네임(프로필명 미리 채움) 한 페이지.
- 기업: 선택 → 약관 → 사업자 인증(번호·개업일·대표자 3개가 API 필수값이라 먼저) → 나머지 정보·사업자등록증 첨부·담당자·자동입력방지 → 완료.
- 수집 확대: 이름·휴대폰 추가 (기존 "이메일·닉네임만" 폐기). 본인인증 위치는 맨 앞 (실연동 시 이름·휴대폰 자동 채움).
- 일반 회원 아이디·비밀번호 찾기는 휴대폰 본인인증 (한국 관례). 이메일 링크는 이메일 계정이 뚫리면 같이 뚫리고, 가입 이메일을 잊으면 못 찾음. 본인인증은 가입 때 어차피 계약.
- 기업 회원 비밀번호 찾기는 사업자번호 + 담당자 이메일 링크 (오픈마켓 셀러센터 관례). 기업 가입에 담당자 본인인증이 없어 대조할 CI 가 없고, 담당자 본인인증을 넣으면 담당자 개인에 계정이 묶임.
- 자동입력방지는 Cloudflare Turnstile (이미 Cloudflare 사용, 무료). 1단계는 자리만.
- 약관 문안은 법무 검토 전 초안. 검토 전 서비스 오픈 금지.

## 2026-09-21 기업 가입은 관리자 심사 후 승인 (사칭 가입 대책)
- 문제: 국세청 진위확인은 "실존 사업자인가"만 확인. 사업자번호·개업일·대표자는 공개 정보라 남의 회사로 가입할 수 있음. 사업자등록증 사본도 마찬가지.
- 결정 (1단계): 가입 직후 `pending`. 로그인은 되지만 사업자 배지·사업자 명의 등록 불가(일반 회원과 동일). 관리자가 사업자등록증·국세청 결과 대조 후 `approved`/`rejected`, 담당자 이메일로 통보. **사업자번호당 계정 1개.** 선점당한 진짜 회사는 이의 신청(사업자등록증 + 대표자 신분증 → 관리자 검토 → 계정 이전).
- 이유: 외부 계약 없이 지금 받는 자료로 가능. 초기 기업 가입은 하루 몇 건이라 수동 심사가 부담 아님. 오픈마켓 셀러센터 관례.
- 대안: 대표자 본인인증(법인은 대표가 직접 가입 안 함), 사업자 계좌 1원 인증(계좌실명조회 API 계약 필요), 공동인증서(과함).

- 한계: 내장 Postgres 에는 **pgvector 확장과 Redis 가 없다.** 그걸 쓰는 테스트(상품 임베딩, refresh 토큰)는 로컬에서 못 돌고 CI(Docker) 에서만 검증된다. 로컬 초록 ≠ 완료. CI 초록이 완료.
- 제거 조건: Docker 를 쓸 수 있게 되면 `build.gradle` 의 zonky 의존성·BOM 과 `TestInfraConfiguration` 의 `DockerUnavailable` 경로를 지운다. `docker compose up` 후 코드 변경 없이 그대로 동작하므로 "옮기는" 작업은 없다.
- **2026-09-22 덧붙임 — Redis 도 같은 방식.** 인증(refresh 세션·로그인 잠금)이 Redis 를 쓰는데 로컬에 없어서 `com.github.codemonstur:embedded-redis`(테스트 전용, Windows 바이너리 포함)를 Docker 없을 때만 띄운다. 사용자 결정: "일단 오늘만 이 계획으로, 도커 되면 뺀다". 제거 시 지울 것: `build.gradle` 의 `embedded-redis` 한 줄, `TestInfraConfiguration` 의 `embeddedRedis`·`embeddedRedisProperties` 빈. 이제 로컬에서 못 도는 건 pgvector 를 쓰는 테스트만.

## 2026-09-22 계정은 사람당 하나를 지향. 소셜 연결 1개, 담당자는 조직 1개, 중복 가입 감지는 CI 또는 이메일

- 이유: 거래 서비스라 계정 여러 개는 사기·제재 회피 통로. 다른 사이트들도 소셜 중복은 이메일로 막는다.
- 한계: 완전한 "한 사람 = 한 계정"은 본인인증(CI)으로만 가능. 일반(아이디) 가입은 CI 유일로 보장되지만 소셜·기업 담당자는 본인인증이 없어 이메일 대조가 최선 — 카카오가 이메일 동의를 안 주거나 제공자별 이메일이 다르면 못 잡음.
- 부작용: 이메일이 전체 유일이라 개인 계정과 기업 담당자 이메일이 같으면 둘 다 못 만듦. 보통 회사·개인 메일이 달라 감수.
- 대안: 소셜·기업 가입에도 본인인증 필수 — 이탈 증가·흐름 수정이 커서 보류. 재검토 조건: 중복 계정 악용 사례가 생기면.

## 2026-09-22 가입 후 자동 로그인 없음. 본인인증은 환경변수로 stub ↔ 실제, 기본값은 거부
- 가입 성공은 `201 { userId }` 만. 완료 화면에서 로그인으로 보낸다. 이유: 한국 서비스 관례이고, 사용자가 비밀번호를 기억하는지 바로 확인된다. 나중에 자동 로그인으로 바꾸는 건 컨트롤러 한 줄.
- 본인인증은 `IdentityVerifier` 인터페이스. `IDENTITY_VERIFICATION_PROVIDER=stub` 이면 프론트의 고정 토큰을 받아 입력한 이름·휴대폰을 인증값으로 치고 CI 를 휴대폰에서 파생(한 사람 = 계정 하나를 휴대폰 기준으로 흉내). **기본값은 `pass`** — 환경변수를 빼먹은 운영에서 stub 이 열리지 않게. 2차 방어로 `APP_ENV=local` 이 아닌데 stub 이면 기동 실패(보안 리뷰: `.env.example` 을 복사한 운영 서버가 stub 으로 뜨는 경로가 있었다). `.env.example` 에는 주석으로만. 실제 구현이 없는 동안 `pass` 는 모든 토큰을 거부(가입 불가). PASS/NICE 계약 후 Redis `signup:verify:{token}` 을 읽는 구현으로 교체하고 stub 클래스 삭제.
- 중복은 미리 확인하고, 동시 가입 경쟁은 유일 제약 이름(`ux_users_login_id` 등) → 오류 코드 매핑으로 잡는다. 같은 CI 는 `ALREADY_REGISTERED`("아이디 찾기 안내") 로 휴대폰 중복보다 먼저.
- 약관 버전은 `TERMS_VERSION` 환경변수(시행일). 법무 검토 전이라 `2026-09-22-draft`. 문안 확정 시 값을 올리면 재동의 대상이 된다.
