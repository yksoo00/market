# 시연 가이드

IT 장비 중고·재고 마켓플레이스를 사람들 앞에서 보여 주기 위한 문서. 세 부분이다.

1. 시연 데이터가 무엇이고 왜 이렇게 만들었나
2. 데이터를 만들고 넣는 방법과 순서
3. 시연 순서 (장면별 클릭·말할 거리·잘못됐을 때)

데이터 전체 목록(계정·매물·거래)은 [data/데이터-목록.md](data/데이터-목록.md), 엑셀을 만드는 스크립트는 [build-demo-data.mjs](build-demo-data.mjs).

### 이야기 한 줄

> 서버실을 새로 짓는 기업(다온소프트)과 쓰던 장비를 정리하는 개인이 있고, 이 둘을 서버·네트워크·PC를 파는 세 곳의 판매자가 받아 주는 중고·재고 장터.

### 상품·매물 — "완벽한 매물"만

미리 넣는 매물은 **사진·데이터시트·상품설명·보증기간·불량지원·대체품·테스트 리포트·정품 확인서가 전부 있는 것만** 둔다. 검색 결과가 어느 줄을 열어도 비어 있지 않게 하려는 것이다.

- 상품 마스터 14종, 매물 16건. 가격은 현실적인 중고 시세, 상태는 `신품`부터 `신품대비 70~79%`까지 섞었다.
- 사진·데이터시트가 제조사 사이트에서 받아지지 않은 상품 17종(DL380, R750, RDIMM, IronWolf, SMT1500IC, 2960-X, 9200L, AP22, PA-220, EliteBook 840 G8, OptiPlex 7090, EliteDesk 800 G6, M720q, LG 27UP850-W, U2723QE, P2422H, MX500)은 미리 넣지 않는다. 그중 LG 27UP850-W·U2723QE 는 다량 등록 시험용으로 쓴다(아래).
- **테스트 리포트·정품 확인서는 시연용 가상 문서**다 (`make-sample-docs.mjs` 가 매물마다 만든다). 모든 장 위·아래에 "시연용 가상 문서"가 적혀 있고, 정품 확인서는 제조사 인증서가 아니라 판매자가 쓴 확인서 형식이다. 사진·데이터시트는 제조사 공식 자료다.
- **같은 소분류에 여러 개 있는 곳** (비교 시연용): 내장형 SSD — Samsung 980 PRO(피씨마루, 개인 판매자 두 곳) · 870 EVO. 서버는 소분류가 갈려 서로 비교되지 않는다.
- **같은 상품을 기업과 개인이 따로 파는 경우**가 2건 있다 (980 PRO, ThinkPad T14).
- **최소주문량이 있는 매물**: UniFi U6 Pro·PM9A3(2개 이상).
- **판매완료 1건**: 개인 판매자의 ThinkPad T14(1개)가 거래 한 건으로 다 팔려 "거래완료"로 보인다.
- **라이브 등록용 상품마스터**: **Synology DiskStation DS1621+ NAS(6베이)** 를 골라 두었다. 마스터에는 사진·데이터시트가 붙어 있고 **매물은 아직 없다** — 시연에서 이 마스터로 매물을 등록한다 (장면 10). 나머지 서류(테스트 리포트·정품 확인서)와 입력값은 `Downloads\판매등록\` 폴더에 있다.

## 2. 데이터 만들고 넣기

### 만들기

```
node docs/demo/build-demo-data.mjs --date <시연하는 날 YYYY-MM-DD>
```

| 옵션 | 뜻 | 기본 |
|---|---|---|
| `--date` | 시연하는 날. 매물 등록일·납품일·거래일이 이 날짜 기준으로 만들어진다. 납품일은 시연일 +3~+22일이라 "납품 가능일" 필터·정렬이 자연스럽다 | 오늘 |
| `--uid-date` | 엑셀을 **가져오는 날**. 서버가 사용자 uid 를 그날 날짜로 새로 만들기 때문에(`UP`+`yyMMdd`+일련번호) 다른 시트가 가리키는 uid 도 같은 날짜여야 한다 | 오늘 |
| `--uid-start` | 가져오는 날 이미 가입한 사용자가 있어 일련번호가 1부터가 아니면 첫 번호 | 1 |

`data/` 폴더에 엑셀 6개(전체 1 + 테이블별 5)와 `데이터-목록.md` 가 생긴다. 헤더는 정의서의 한글 논리명 그대로다 (정의서의 오타 "시용자ID", "개업년원일"도 그대로 — 임시 테이블 화면이 그 이름을 받는다).

> **날짜가 중요하다 (자동 키 규칙이 들어가기 전).** 가져오는 날 밤 12시를 넘기면 uid 날짜가 달라진다. 가져오는 날과 `--uid-date` 가 다르면 다시 만든다. 사용자 엑셀을 가져온 직후 아래 "확인 1"로 uid 를 꼭 본다. 외래키가 없어서 uid 가 어긋나도 오류 없이 들어가고, 시연에서 매물·거래가 엉뚱하게 보인다. 자동 키 규칙이 들어간 뒤에는 서버가 새 uid 로 참조를 맞추므로 이 걱정이 줄지만, "확인 1"은 그대로 해 둔다.

### 시연 전 준비 (한 번)

- [ ] DB 가 깨끗한가? 개발용 샘플 `PD-0108-001~050` (Hitachi, `db/seed`) 이 들어 있으면 상품 찾기 목록에 섞여 보인다. 시연용 DB 는 `.env` 의 `FLYWAY_LOCATIONS` 에서 `classpath:db/seed` 를 빼고 띄우거나, 그 50건을 지운다 (매물이 없는 마스터라 지워도 안전).
- [ ] 같은 날 이미 가입한 사용자가 없는가? 있으면 `--uid-start` 를 맞춘다.
- [ ] `.env` 에 `APP_ENV=local` (임시 테이블 화면 + 가져오기). 개인 가입을 시연하려면 `IDENTITY_VERIFICATION_PROVIDER=stub` 도 필요하다 (`.env.example` 참고).
- [ ] `docker compose up -d` → 백엔드 → 프론트 실행.

### 넣는 방법 두 가지

임시 테이블 화면(`/dev/tables`)으로 넣는다. 파일이 두 종류다.

| 방법 | 파일 | 화면 버튼 | 언제 |
|---|---|---|---|
| **A. 한 번에 (권장)** | `00_전체.xlsx` (시트 5개) | 엑셀 전체 불러오기 | 평소. 서버가 부모 → 자식 순서로 한 트랜잭션에 넣고, 하나라도 실패하면 전부 되돌린다 |
| B. 테이블별 | `01`~`05_*.xlsx` | 이 테이블 엑셀 불러오기 | 한 테이블만 다시 넣거나 내용을 따로 보여 줄 때 |

> **브랜치 `feat/dev-table-auto-keys` 와의 관계.** 이 문서를 쓰는 동안 그 브랜치에 "임시 테이블이 주 PK·시각을 서버 규칙대로 새로 만들고, **같은 파일 안에서만** 참조를 새 키로 맞춘다"는 커밋(`a96c99b`)이 올라왔다. 그 규칙이 들어가면:
> - 방법 A 는 그대로 된다. 파일 안의 옛 키(uid·상품ID·등록일시·거래ID)를 서버가 새 키로 바꿔 가며 참조를 맞춘다. 사용자 시트에 `사용자식별자` 칸을 넣어 둔 이유다.
> - 방법 B 는 **테이블별로 따로 넣으면 뒤 시트가 앞 시트의 새 키를 못 찾아 거절**된다 (상품ID·등록일시·거래ID 가 새로 만들어지므로). 그 브랜치가 머지된 뒤에는 방법 A 만 쓴다.
> - 등록일시·거래 등록일시는 가져온 시각으로 바뀐다 (엑셀의 과거 날짜는 무시). 그래서 매물의 등록 시각이 "13일에 걸쳐 분포"하지 않고 전부 가져온 시각 근처가 된다. 납품일·확정일시·재고·상태는 엑셀 값 그대로다.
> - **알려진 문제 (아래 "5. 한계" 참고):** 같은 판매자의 서로 다른 상품 매물이 같은 등록일시를 받던 문제는 `fix/dev-table-listing-reg` 로 고쳤다. 그 수정이 머지되기 전에는 "확인 5"가 0줄이 아닐 수 있다.

**방법 B 의 순서.** 외래키는 없지만 **다른 시트가 앞 시트의 키를 가리키므로** 아래 순서로 넣는다. 한 파일 안에서 한 행이라도 실패하면 그 파일은 통째로 되돌려진다.

| 순서 | 파일 | 테이블 | 행 | 먼저 넣는 이유 |
|---|---|---|---|---|
| (이미 있음) | — | 카테고리 코드·마스터 | 239 | 마이그레이션이 넣음. 상품 마스터의 대·중·소 코드가 여기 있는 값이다 |
| 1 | 01_trd_user_info.xlsx | 사용자 정보 | 7 | uid 가 여기서 만들어진다. 뒤의 모든 시트가 이 uid 를 쓴다 |
| 2 | 02_trd_prod_master.xlsx | 상품 마스터 | 15 | 매물이 상품고유ID로 가리킨다 (자동 키 규칙이 들어간 서버는 가져올 때 새 번호로 바꿔 맞춘다) |
| 3 | 03_trd_prod_reg.xlsx | 상품등록 정보(매물) | 16 | 거래가 판매자 uid + 등록일시 + 상품ID 세 값으로 매물을 가리킨다 |
| 4 | 04_trd_trade_info.xlsx | 거래 정보 | 18 | 매물이 있어야 의미가 있다. 재고는 이미 매물에 반영돼 있다 |
| 5 | 05_trd_trade_history.xlsx | 거래이력 정보 | 8 | 구매확정된 거래 8건과 짝이다 |

비밀번호는 평문(`Demo1234!@`)으로 들어 있고, 서버가 가져올 때 bcrypt 로 바꿔 저장한다. 사용자 엑셀의 `사용자식별자` 칸은 서버가 무시하고 가져오는 날 기준으로 새로 만든다 (`UP`+`yyMMdd`+일련번호). 다만 `feat/dev-table-auto-keys` 가 머지되기 전에는 다른 시트가 엑셀에 적힌 uid 를 그대로 쓰므로, 그때는 아래 "확인 1" 이 꼭 필요하다.

### 확인 (psql)

접속: `docker compose exec postgres psql -U <POSTGRES_USER> -d <POSTGRES_DB>` (값은 `.env`).

**확인 1 — 사용자 엑셀 직후.** uid 가 `UP<가져온 날 yyMMdd>001` ~ `007` 이어야 한다.

```sql
select uid, user_id, user_class from trd_user_info order by uid;
```

**확인 2 — 전부 넣은 뒤.** 행 수 (사용자 7 · 마스터 15(매물에 붙은 14 + 라이브 등록용 DS1621+ 1) · 매물 16 · 거래 18 · 이력 8).

```sql
select (select count(*) from trd_user_info)          as users,
       (select count(distinct prod_id) from trd_prod_reg) as listed_masters,
       (select count(*) from trd_prod_master where prod_name = 'DiskStation DS1621+ NAS 6베이') as live_master,
       (select count(*) from trd_prod_reg)           as listings,
       (select count(*) from trd_trade_info)         as trades,
       (select count(*) from trd_trade_history)      as history;
```

**확인 3 — 재고가 거래와 맞는가.** 결과가 0줄이어야 한다.

```sql
select r.user_id, r.reg_date, r.prod_id, r.sales_quantity, r.stock_quantity
from trd_prod_reg r
left join trd_trade_info t
  on t.seller_id = r.user_id and t.prod_reg_date = r.reg_date and t.prod_id = r.prod_id
group by r.user_id, r.reg_date, r.prod_id, r.sales_quantity, r.stock_quantity
having r.stock_quantity <> r.sales_quantity
  - coalesce(sum(t.order_quantity) filter (where t.trade_stats in ('견적수락','구매요청','구매확정')), 0);
```

**확인 4 — 거래가 가리키는 매물이 있는가.** 결과가 0줄이어야 한다 (uid 가 어긋났을 때 여기서 걸린다).

```sql
select t.trade_id from trd_trade_info t
left join trd_prod_reg r
  on r.user_id = t.seller_id and r.reg_date = t.prod_reg_date and r.prod_id = t.prod_id
where r.user_id is null;
```

**확인 5 — 매물 주소가 하나씩인가.** 결과가 0줄이어야 한다. 매물 상세 주소가 `(판매자 uid, 등록일시)` 두 값으로 매물을 찾기 때문에, 같은 판매자의 매물이 같은 등록일시를 가지면 그 상세 화면이 오류가 난다 (`ListingRepository.findByUserIdAndRegDate` 는 한 건만 기대).

```sql
select user_id, reg_date, count(*) from trd_prod_reg group by user_id, reg_date having count(*) > 1;
```

```sql
begin;
create temp table demo_uid as

  where user_id in ('hanbit01','netone01','pcmaru01','daon01','seoyeon01','minjun01','jiwoo01','guest2026');

delete from trd_trade_history  where user_id in (select uid from demo_uid) or seller_id in (select uid from demo_uid);
delete from trd_trade_info     where user_id in (select uid from demo_uid) or seller_id in (select uid from demo_uid);
delete from trd_prod_reg       where user_id in (select uid from demo_uid);
delete from trd_prod_master    where prod_id in (select prod_id from demo_prod)
                                  or prod_name in ('DiskStation DS1621+ NAS 6베이',        -- 장면 10 라이브 등록용 마스터
                                                   '27UP850-W 27인치 4K UHD 모니터',       -- 장면 12 다량 등록이 새로 만든 상품

```

이후 확인 1부터 다시. 오늘 가입자가 모두 지워졌다면 uid 는 001부터 다시 시작한다. 다른 사용자가 남아 있으면 `--uid-start` 를 맞춰 엑셀을 다시 만든다.

## 3. 시연 순서

총 40분 안팎 (장면 1~13). 장면 하나는 1~5분이다. 25분으로 줄여야 하면 **장면 2·5·7·11 과 13 을 건너뛰고 1, 3, 4, 6, 8, 9, 10, 12 만** 한다.

### 시작 전 세팅

- 브라우저 창 세 개로 계정을 나눠 둔다. 쿠키가 창마다 갈리게 **Chrome 일반 창 / Chrome 시크릿 창 / Edge** 로 한다.
  - 창 A (Chrome 일반): 판매자 — `netone01` 로 시작(장면 6·7), 장면 9 직전에 로그아웃하고 `hanbit01` 로 다시 로그인(장면 9·10)
  - 창 B (시크릿): 구매자 — 장면 3 에서 가입하는 `guest2026`
  - 창 C (Edge): 예비 — `daon01` (거래이력·미리 만든 `견적수락` 거래 시연 / 장면 3 가입이 막힐 때 대신 쓴다)
- 라이브 등록(장면 10)에 올릴 파일은 `Downloads\판매등록\` 에 이미 있다 (사진·데이터시트·테스트 리포트·정품 확인서 + 입력값 메모). 다량 엑셀(장면 12·13)은 `Downloads\다량-엑셀\` 에 있다.
- 화면은 넓은 데스크톱(분할 화면이 열리는 폭)으로 연다. 마지막으로 모바일 폭(390px)을 잠깐 보여 줄 수 있다.
- 세 창을 모두 로그아웃 상태에서 시작한다. 창 A·C 는 시연 직전에 로그인해 둔다.

### 장면 1 — 첫인상: 홈과 검색 (비로그인, 2분)

1. 홈을 연다. "IT 장비 중고·재고 거래 장터"라고 한 줄 소개.
2. 헤더 `∷ 판매·구매 메뉴 → 상품검색 · 견적 요청` 으로 검색 화면을 연다. 기본 조건이 "거래 가능"이라 검색결과는 **15건**이다 (다 팔린 개인 판매자의 ThinkPad T14 1건은 상태를 `전체`·`거래완료`로 바꿔야 보인다).
3. 검색어 `서버` → R650 · SR650 · T350 세 건. 목록 줄마다 사진·데이터시트·보증·불량지원·대체품·테스트 리포트·정품인증서 칸이 **전부 채워져** 있다 (검색 결과 열: 사진·데이터시트·보증기한·불량지원·대체품·테스트리포트·정품인증서).

**말할 거리**: 로그인하지 않아도 매물은 볼 수 있다. 판매자는 회사 이름으로 보이고 연락처는 어디에도 노출되지 않는다. 올라와 있는 매물은 서류가 다 갖춰진 것만이다.

### 장면 2 — 검색·필터·상세 (2~3분)

1. 검색어를 지우고 카테고리를 `기업용 → 서버 → 랙마운트 서버` 로 좁힌다 (R650 1U, SR650 2U).
2. 정렬을 가격 낮은순으로 바꾼다 (최신순이 아니면 페이지 번호 방식으로 나온다). SR650(210만) → R650(580만).
3. 상태 필터를 걸어 본다 (`신품대비 90~99%` 이상만 → R650 한 건).
4. 매물 하나(SR650)를 열어 상세를 보여 준다. 사진, 상품상태 `신품대비 70~79%`, 보증기간, 불량지원 `환불`, 대체품 글, 그리고 **데이터시트·테스트 리포트·정품 확인서 PDF 를 눌러 열어 본다** — 이 서류는 비공개 파일이라 **로그인해야 열린다**(사진만 공개). 비로그인 상태로는 칸의 있음/없음만 보이므로, 서류를 직접 열어 보이는 건 장면 3 에서 로그인한 뒤 이 매물로 돌아와서 한다.

**말할 거리**: 상품 상태를 "신품대비 N%" 구간으로 표준화해 두어서, 판매자마다 제각각인 중고 상태 표현을 같은 기준으로 걸러 볼 수 있다. 서류가 매물에 붙어 있어 구매 전에 확인할 수 있다.

> 필터·정렬 컨트롤의 정확한 위치는 리허설 때 한 번 눌러 보고 대본에 적어 둔다. 이 문서는 코드의 필터 이름(카테고리·상태·가격·납품일·정렬)만 보고 썼다.

### 장면 3 — 개인 가입 (라이브, 3분)

헤더 [로그인] → [가입] → 개인.

| 칸 | 입력 |
|---|---|
| 본인인증 | 버튼 누르면 바로 성공 (개발용 임시 인증) |
| 이름 | 홍길동 |
| 별칭 사용 | 켜고 `시연손님` → [중복확인] |
| 아이디 | `guest2026` → [중복확인] |
| 이메일 | `guest2026@example.com` |
| 비밀번호 | `Demo1234!@` (확인란 동일) |
| 휴대폰 | 010 / 5550 / 9999 |
| 약관 | 전체 동의 |

1. 약관 동의 전에는 [가입] 버튼이 꺼져 있음을 보여 준다.
2. 일부러 비밀번호 칸에 `abc` 를 쳐서 빨간 안내문(10자 이상, 영문·숫자·특수문자)이 뜨는 걸 보여 준 뒤 고친다.
3. 가입 완료 팝업 → 로그인 화면 → `guest2026` 로 로그인 (창 B).

**말할 거리**: 입력은 브라우저에서 즉시 검사하고, 서버가 같은 규칙으로 한 번 더 검사한다.
**막히면**: 가입이 안 되면 창 C 의 `daon01` 로 이후 장면을 진행한다 (장면 6·8 은 `daon01` 의 미리 만든 거래로 대체).

### 장면 4 — 비교 (창 B, 2분)

1. 검색어 `SSD` → Samsung 980 PRO (피씨마루) · 980 PRO (개인 판매자) · 870 EVO 세 건을 체크 → 소분류가 같으므로 [비교에 담기] 가 켜진다.
2. 일부러 다른 소분류(예: 마우스 MX Master 3S) 한 건을 같이 체크해 보면 담기가 막히는 걸 보여 준다.
3. 세 건 담기 → [비교 보기] → 비교 표. "최저가"가 개인 판매자 980 PRO(115,000원)로 표시되고, "다른 항목만 보기"로 차이(상태·단가·보증·서류)만 남긴다.
4. 비교 표에서 [빼기]로 한 건씩 빼 본다. 한 건만 남으면 2개 이상 담으라는 안내가 뜨는지 리허설에서 확인해 두고, 안 보여 줄 거면 이 단계는 뺀다.

**말할 거리**: 같은 종류끼리만 비교하게 막아 두었다. 같은 상품이라도 기업과 개인의 보증·서류 차이가 한눈에 보인다.

### 장면 5 — 장바구니 (창 B, 3분)

1. 검색어 `SSD` → 980 PRO (피씨마루) · 870 EVO 를 체크 → [장바구니]. (장면 4 의 비교에 담긴 줄과는 별개다.)
2. 헤더 장바구니 숫자가 올라간다 → 장바구니 화면.
3. 수량을 +/- 로 바꿔 본다. 재고(870 EVO 38개)보다 많이 넣으면 그 칸에 오류가 뜬다.
4. `980 PRO`(피씨마루, 재고 49) 줄을 [구매] 한다 → 구매요청이 되고 장바구니에서 빠진다. 나머지는 [빼기].

**말할 거리**: 장바구니에 담으면 그 수량만큼 재고가 묶이고, 1시간이 지나면 풀린다.
**주의**: 870 EVO 에는 미리 만든 구매요청(재고 38)이 걸려 있어 구매는 980 PRO 로 한다.

### 장면 6 — 견적 요청 (창 B → 창 A, 4분)

이 장면이 서비스의 핵심이다. 구매자가 가격을 제안하고 판매자가 답한다.

**구매자 (창 B, `guest2026`)**

1. 검색어 `UniFi` → `UniFi Switch Pro 24 PoE`(89만 원, 재고 7) 체크 → [견적 요청].
2. 수량 2, 희망단가 `850000`, 납품희망일은 기본값(제공가능일) 그대로, 요청사항 "사무실 신축 PoE 스위치용".
3. 희망단가를 등록단가(89만 원)보다 **높게** 넣어 오류가 뜨는 것도 보여 준다 (희망단가는 1 ~ 등록단가).
4. 내 구매목록 / 견적 확인에서 상태가 `견적요청` 이고 [취소] 만 있음을 본다.

**판매자 (창 A: `netone01` 로 로그인)**

5. `∷ 메뉴 → 판매 견적 조정` 에 받은 견적요청이 **2건**: 미리 만든 FortiGate 60F(다온소프트)와 방금 만든 `guest2026` 요청.
6. `guest2026` 의 요청을 [수락]. FortiGate 는 두고, 나중에 장면 7 에서 [거절]을 보여 준다.
7. 수락해도 **매물 단가는 그대로 89만 원**이다. 수락한 수량 2개만 재고에서 묶인다 (재고 7 → 5).

**말할 거리**: 수락하면 그 수량이 구매자 몫으로 묶여서 다른 구매자가 가져갈 수 없다.

### 장면 7 — 거절과 재요청 (창 A → 창 C, 2분)

1. 창 A (`netone01`): FortiGate 60F 견적요청을 [거절]. 확인창에 "매물 단가는 그대로예요" 문구.
2. 창 C (`daon01` 로 로그인): 견적 확인 → `거절됨` 줄은 [재요청]·[취소] 만 있고 [구매] 는 없다. 희망단가를 높여 [재요청] → 같은 줄이 `견적요청` 으로 돌아간다 (새 줄이 생기지 않음).
3. (선택) 미리 만든 **수락된 견적**(RTX A4000, 희망 74만 원, 수량 1)에서 [구매] → 구매요청.

**말할 거리**: 거절은 끝이 아니라 협상의 한 단계다.

### 장면 8 — 구매와 거래완료 (창 B, 3분)

1. 창 B: 견적 확인 → `guest2026` 의 UniFi 견적이 `수락됨` 으로 바뀌었다. [구매] → 수량·단가는 수락된 값(2개)으로 고정, "바꾸려면 취소하고 다시 견적하세요" 문구.
2. 구매요청이 되면 내 활동내역 → 구매 탭에 `구매요청` 줄. [거래완료] → "물건을 받으셨나요?" 확인 → 구매확정.
3. 내 메뉴 → 내 거래이력에 확정된 거래가 올라온다.

**말할 거리**: 확정하면 취소할 수 없고, 확정 전에는 구매자·판매자 누구나 취소할 수 있다.

### 장면 9 — 판매자의 견적 한꺼번에 처리 (창 A, 3분)

1. 창 A: `hanbit01` 로 로그인 → `판매 견적 조정` → [모든 견적요청 보기].
2. 같은 상품끼리 묶여 있다. **T350 타워 서버**는 2건(3개 + 3개 = 6개)이 재고 5개를 넘어 "재고를 넘어요 — 모두 수락하면 이 묶음은 실패해요" 안내가 보인다. SR650 한 건(희망 200만 원)은 정상.
3. [모두 수락] → SR650 은 수락되고 T350 묶음은 사유와 함께 실패한다.
4. T350 을 건별로 보고 첫 건만 [수락] → 둘째 건은 재고 부족 사유가 그 줄에 뜬다.

**말할 거리**: 판매자가 요청이 많이 들어와도 재고를 넘기는 약속을 하지 않도록 시스템이 막는다.

### 장면 10 — 판매 등록 (라이브, 창 A `hanbit01`, 5분)

**고른 상품마스터: Synology DiskStation DS1621+ NAS (6베이).** 이미 마스터로 들어 있어 [상품 찾기]에서 고르면 제조사·카테고리·사양·사진·데이터시트가 자동으로 채워진다. `Downloads\판매등록\` 폴더를 열어 두고 `00_입력값.txt` 를 보면서 입력한다. 등록은 두 단계다.

**1단계 — 판매상품 등록** (`∷ 메뉴 → 판매상품 등록`)

1. 처음엔 상품 칸이 잠겨 있다. [상품 찾기]를 눌러 `DS1621` 을 검색 → **DiskStation DS1621+ NAS 6베이** 를 고른다 → 카테고리(기업용 → 기업용 스토리지 → SAN/NAS → 기타)·제조사 Synology·파트넘버·사진·데이터시트가 채워진다.
2. 매물 값을 입력한다: 상품상태 `신품대비 90~99%`, 단가 `880000`, 수량 `3`, 최소주문 1, 주문단위 1, 제공가능일 시연일 + 7일, 설명 (`00_입력값.txt`).
3. 마스터 사진이 대표 사진으로 쓰이므로 사진은 따로 안 올려도 된다 (같은 파일 `01_사진_DS1621+.png` 가 폴더에도 있다 — 바꿔 올리고 싶을 때).

**말할 거리**: 구매자가 필요한 조건(상태·보증·서류)을 엑셀에 적어 두면, 그 조건에 맞는 매물만 찾아 준다. 서류가 다 있는 매물만 올라와 있기 때문에 조건이 높아도 걸리지 않는다.
**참고**: 이 화면의 정확한 버튼 이름·흐름은 리허설 때 확인한다 (코드의 파서·조건 규칙만 보고 썼다). 파일이 서버 파서(`CartBulkParser`)로 10줄 모두 읽히는 것까지만 확인했다.

## 5. 한계 (확인하지 않은 것)

- **임시 테이블의 매물 등록일시 충돌 (수정함, 머지 대기).** 자동 키 규칙이 한 판매자의 서로 다른 상품 매물에 같은 `reg_date` 를 주던 문제를 `fix/dev-table-listing-reg` 브랜치(커밋 8ee760d)에서 판매자 단위로 고쳤다. 매물 상세·수정은 `(판매자 uid, 등록일시)` 로 한 건을 찾기 때문이다. 이 브랜치가 `dev` 에 머지되기 전의 `dev`(자동 키 규칙 포함)에 이 데이터를 넣으면 상세 화면이 오류날 수 있으니 위 "확인 5" 로 꼭 확인한다.

- **리허설 결과 (2026-11-23, 격리된 테스트 DB).** `00_전체.xlsx` 를 `/api/v1/dev/import` 로 실제로 넣고 시연에서 누르는 API 를 호출했다. 통과: 사용자 7·마스터 14·매물 16·거래 18·이력 8 가져오기, uid·키 대응, 재고·거래 연결 SQL(확인 3·4), 7계정 로그인(개인 3·기업 4), 거래 가능 검색 15건·'서버' 3건·SSD 소분류 3건, 매물 상세 16/16, 공개 사진 200·비공개 서류 비로그인 401·로그인 200(PDF), 판매자 견적 수락(재고 6→4)·구매자 거래완료(이력 4→5), 받은 견적요청 조회, 다량 등록(8 MATCHED·2 NEW_MASTER·실패 0, 확정 10건, 새 상품 사진은 ZIP 에서 매물에 붙음), 대량구매 10줄 전부 조건에 맞는 매물 발견.
  - **수정 전 `dev` 에서는 실패했다**: 같은 판매자의 매물이 같은 `reg_date` 를 받아 확인 5 가 걸리고 매물 상세 14/16 이 HTTP 500. `fix/dev-table-listing-reg` 를 적용하니 16/16. **그 브랜치를 `dev` 에 머지하기 전에는 이 데이터를 넣지 않는다.**
  - 다량 등록으로 새로 생긴 상품의 **마스터에는 이미지가 안 붙는다**(그 상품의 매물에는 ZIP 사진이 붙는다). 마스터 사진이 필요하면 판매상품 등록에서 새로 올린다.
  - **화면 클릭은 못 돌렸다.** API 까지만 확인했다. 필터·정렬·모달 버튼 이름과 위치는 리허설에서 눈으로 본다.
  - 개발 서버(`api-dev`)는 `./backend/data/uploads` 를 마운트하므로 이 PC 에서는 파일이 그대로 열린다.
- **사진·데이터시트가 있는 상품만 넣었다.** 제조사 공식 사진·데이터시트를 `fetch-product-files.mjs`(제조사 사이트에서 받기)·`extract-pdf-photos.mjs`(PDF 안 제품 사진)·`add-local-photo.mjs`(직접 받은 사진 넣기)로 모았다. 파일은 `backend/data/uploads/` 에 업로드 API 와 같은 키로 저장되고(`.gitignore` 대상이라 저장소에 안 올라간다), 키와 출처는 `assets/manifest.json` 에 있다. **다른 컴퓨터에서 시연하면 `backend/data/uploads/` 를 같이 복사**해야 파일이 열린다.
  - 제조사 사이트가 스크립트 내려받기를 막아(403·429) 받지 못한 상품 17종은 미리 넣지 않았다. 사진·데이터시트를 직접 받아 `add-local-photo.mjs`·manifest 로 채우면 `build-demo-data.mjs` 가 그 상품을 매물에 포함한다.
  - 일부 "데이터시트"는 그 모델 단독 문서가 아니다: WD Red Plus(시리즈 문서), PM9A3(시리즈 문서), ThinkPad T14(PSREF 사양서), 980 PRO·870 EVO(시리즈 데이터시트), MX Master 3S(비즈니스 모델 데이터시트) 등.
  - **저작권**: 사진·데이터시트는 각 제조사 자료이고 일부 사진은 판매점 페이지에서 받았다(출처는 manifest). 내부 시연에만 쓰고 저장소·공개 자료에 올리지 않는다.
- **테스트 리포트·정품 확인서는 가상 문서다.** 실제 검사·인증 결과가 아니며 문서마다 그렇게 적혀 있다. 진짜 서류로 오해되지 않게 시연 때 "샘플 문서"라고 한 마디 한다.
- **물품분류번호**(`prod_class_no`)는 시연용 예시 값이다 (실제 조달청 분류와 다를 수 있다).
- **다량 등록·대량구매 엑셀(10줄씩)** 은 서버 파서(`ListingBulkParser`·`CartBulkParser`)로 10줄 모두 읽히는 것까지만 확인했다. 검사·확정·장바구니 담기 화면은 돌려 보지 않았다.
