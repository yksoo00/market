# 구매 (구매요청·거래완료·취소) 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 매물을 단가 그대로 구매요청하고, 구매자가 거래완료로 확정하거나 구매자·판매자가 취소하는 흐름과 그 목록 화면을 만든다.

**Architecture:** 새 도메인 패키지 `trade`(엔티티 2개·서비스·컨트롤러). 매물 재고·스냅샷은 `ListingService`의 새 메서드로만 다룬다(도메인 간 service 경유 규칙). 재고는 조건부 UPDATE 한 문장으로 줄여 락 없이 음수 방지. 프론트는 구매 모달 1개 + 거래 목록 컴포넌트 1개를 구매자·판매자 두 화면이 같이 쓴다.

**Tech Stack:** Spring Boot 4.1 / JPA / Flyway / Testcontainers, Next.js 16 / zod / Vitest / Playwright.

**Spec:** `docs/superpowers/specs/2026-10-15-purchase-design.md`

## Global Constraints

- 테이블·컬럼 물리명은 스펙 "데이터" 표 그대로 (`trd_trade_info`, `trd_trade_history`, `seller_id`, `buyer_id` …). 새 이름을 만들지 않는다.
- 코드 값은 한글 문자열: `trade_type` = `구매요청`/`구매확정`/`구매취소`, `trade_stats` = `구매요청`/`구매확정`/`취소`, HISTORY `trade_type` = `구매확정`. 변환은 enum 한 곳.
- `trade_id` = `yyMMddHH`(Asia/Seoul) + `%03d` 순번, 11자. 날짜 칸 `yyyyMMddHHmmss`(14자), 납품희망일 `yyyy-MM-dd`.
- 주문량 1~100000, 최소주문량 이상, 주문단위 배수, 재고 이하. 요청사항 ≤100자. 금액 `단가×수량` ≤ `Integer.MAX_VALUE`.
- 단가는 등록단가 고정 — 요청 DTO에 단가 필드 없음. 본인 id 는 `@AuthenticationPrincipal`에서만.
- 구매요청 rate limit `trade:create:<userId>` 20회/1시간 `hitUnlessInvalid`, `Idempotency-Key` scope `trade-create`.
- 응답에 이메일·전화 없음. 상대방은 `user_nickname`만.
- 사용자 문구는 `frontend/src/messages/trade.ts`. 오류 코드 이름 = 프론트 `trade.errors` 키.
- 스키마 커밋은 `db/trade-tables` 브랜치, 코드는 그 위에 쌓은 `feat/purchase` 브랜치. 각자 PR.

## 스펙과 달라진 점 (구현 중 발견, 사용자 확인 필요)

- **`pendingTradeCount`를 매물 검색 응답에 넣지 않고 `GET /api/v1/trades/pending-counts`로 따로 준다.** 매물 서비스가 거래 서비스를 부르면 `trade → listing → trade` 순환 의존이 된다(backend.md: 도메인 간은 service 경유, 역참조 금지). 내 판매글 화면이 두 API를 같이 부른다.
- **검색 결과의 [구매]는 체크한 매물이 정확히 1개일 때만 모달을 연다.** 지금 검색 결과는 여러 개를 체크해 [구매]를 누르는 구조인데, 모달은 매물 1개용이다. 2개 이상이면 "구매는 한 번에 한 매물씩" 안내.
- 매물 삭제의 "거래 있음" 검사는 FK 위반(`DataIntegrityViolationException`)을 409로 바꾼다 — 매물 서비스가 거래 테이블을 직접 보지 않게.

## Review Focus

1. 같은 매물에 동시 구매요청 → 재고 합계를 넘는 요청은 반드시 하나가 409. (Task 4 동시성 테스트)
2. 같은 거래에 구매자 [거래완료]와 판매자 [취소]가 동시에 → 둘 중 하나만 성공, 재고·이력이 한 번만 바뀜. (Task 5 테스트)
3. 재고가 정확히 0이 되는 요청 → `dt_expire` 들어감, 그 거래 취소 → 지워지고 매물 PATCH 다시 됨. (Task 3·5 테스트)
4. 요청 응답이 유실돼 같은 `Idempotency-Key`로 재전송 → 재고가 두 번 줄지 않고 처음 거래를 돌려줌. (Task 4 테스트)
5. 납기일 없는 매물 + 납품희망일 비움 → 프론트 필드 오류·버튼 꺼짐, 서버도 400 `fields.reqDeliDate`. (Task 7·4 테스트)
