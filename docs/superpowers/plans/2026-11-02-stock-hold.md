# 재고 묶기와 견적 수락 — 계획

## 설계

### 왜
사용자 지시(2026-11-02):
- 견적을 수락하면 **매물 단가가 바뀌어** 다른 사람이 그 값으로 살 수 있다 → 그 거래 안에서만 수락 단가를 쓴다.
- 수락한 견적이 다른 사람에게 먼저 팔리면 안 된다 → 수락하면 그 수량을 구매자 몫으로 묶는다.
- 재고가 0이 됐다고 바로 "판매완료"가 아니라, 구매가 **확정**돼서 0이 돼야 판매완료.
- 수락된 견적에 [구매]만 있고 [취소]가 없다.

### 지금 (코드 기준)
- 재고는 **구매요청**을 보낼 때만 깎인다(`reserveStock`). 그때 재고가 0이 되면 같은 UPDATE 가 `dt_expire`(판매완료)도 켠다.
- 견적요청·장바구니 담기는 재고를 안 건드린다(장바구니는 재고가 모자라도 담긴다).
- 견적 수락(`applyQuotePrice`) = **매물 단가를 희망단가로 내림**. [구매]는 그 매물 단가로 새로 재고를 예약한다.
- 수락된 견적(견적수락)은 취소할 수 없다.

### 사용자 결정 (질문 3개 + 확인 1개)
| 항목 | 결정 |
|---|---|
| 장바구니 | **담으면 수량을 묶고, 1시간 뒤 자동으로 장바구니에서 빠지며 수량이 풀린다** |
| 견적요청 | **묶지 않는다** (견적하는 사이 다른 사람이 사면 판매자에겐 좋은 일) |
| 견적 수락 | **수락하는 순간부터 그 수량을 구매자 몫으로 묶는다.** 구매자가 [취소]하거나 판매자가 취소하면 풀린다. 방치돼도 사람이 풀 때까지 묶인다 |
| 수락 후 [구매] | **수락한 수량 그대로 고정.** 수량을 바꾸려면 취소하고 새로 견적 |
| 판매완료 | 구매 **확정** 때만(아래) |
| 같은 매물 또 담기 | **합치지도 바꾸지도 않고 담을 때마다 새 줄(새 거래)을 만든다.** 날짜·수량이 같아도 따로. 각 줄이 자기 수량을 묶고 자기 1시간을 센다 |
| 담기 검증 | 담기 창에서 재고 초과를 바로 막고(칸별 오류·[담기] 비활성), 서버가 최종 판정해 **틀린 줄에만** 오류를 붙이고 첫 틀린 칸으로 포커스 |
| 장바구니 화면 | 내가 **담은 수량·납품희망일** 열을 표에 더한다(검색과 같은 열은 그대로 두고 오른쪽에) |

### 동작 설계
**"묶음" 표현** — 새 컬럼·테이블 없음. 지금처럼 `stock_quantity` 를 묶는 순간 깎고(`reserveStock`), 풀 때 되돌린다(`releaseStock`). 즉 `stock_quantity` = 아직 아무도 안 묶은 수량. 묶인 건은 거래 행(`trd_trade_info`)의 상태로 안다: 장바구니(구매검토)·견적수락·구매요청.

| 사건 | 재고 |
|---|---|
| 장바구니 담기 | 수량만큼 묶음 (모자라면 담기 실패 — 아래 가정 1) |
| 장바구니 빼기·1시간 만료·매물 삭제 | 되돌림 |
| 장바구니 → 구매요청 | 담은 수량을 풀고 요청 수량을 묶음(한 트랜잭션) |
| 장바구니 → 견적요청 | 담은 수량을 풀음 (견적은 안 묶음) |
| 견적요청·거절·취소 | 변화 없음 |
| **견적 수락** | 견적 수량을 묶음 (모자라면 수락 실패) |
| 수락된 견적 [구매] | 이미 묶여 있어 변화 없음 (단가 = 수락 단가, 수량 = 수락 수량 고정) |
| 수락된 견적 [취소] (신규) | 되돌림 |
| 구매요청·취소 | 구매요청 때 묶음(지금과 같음) / 취소하면 되돌림 |
| 구매 **확정** | 변화 없음(이미 깎여 있음) — 여기서 판매완료 판정 |

**판매완료(`dt_expire`)** — `reserveStock` 이 재고 0이 되면 켜던 걸 **끈다**. 대신 구매 확정(`complete`) 때: 그 매물의 `stock_quantity = 0` 이고 **더 묶인 건(장바구니·견적수락·구매요청)이 없을 때만** 매물에 판매완료를 찍는다. 묶인 건이 취소돼 재고가 돌아오면 판매완료가 아니라 그냥 "거래 중"이다(`releaseStock` 은 `dt_expire` 도 지우므로 그대로 안전).
- 그래서 재고 0·판매완료 아님 = "거래 중인데 지금 살 수량 없음". 화면 표시는 아래 가정 3.

**견적 수락 단가** — `applyQuotePrice` 호출을 없앤다. 거래 행의 `order_unit_price`(희망단가 = 수락 단가)가 이미 있어, [구매]는 매물 단가가 아니라 이 값을 쓴다. 매물(`trd_prod_reg`) 단가·수정일시는 그대로.

**장바구니 1시간 만료** — 담은 지 1시간 지난 행(`trd_trade_info.reg_date` 기준)을 지우고 묶음을 푸는 처리가 필요하다. 쓸 때가 아니라 **재고를 풀어야 하므로 실제 정리**가 있어야 한다.
- 매분 도는 `@Scheduled` 작업 1개 (`@EnableScheduling` 추가, 라이브러리 추가 없음).
- 컨테이너 2개(무중단 배포)가 동시에 돌아도 안전하게: 행 삭제를 조건부(`delete ... where trade_id = ? and trade_stats = 'cart'` 가 1행일 때만 재고를 되돌림)로 해 한 번만 풀린다. 한 행씩 트랜잭션.
- 서비스 stateless 규칙 위반 아님(상태는 DB).

**수락된 견적 [취소]** — 구매자·판매자 누구나(구매요청 취소와 같음). 행을 지우고 재고를 되돌린다. 상대에게 메일은 기존 취소 메일(`QUOTE_CANCELED`)을 쓴다(가정 4).

### 같은 매물 여러 줄 — 영향 (사용자 결정 반영)
지금은 장바구니가 "구매자·매물당 1줄"을 전제로 한다. 줄이 여럿이 되면 바뀌는 곳:
- **DB(마이그레이션)**: `ux_trd_trade_info_one_cart` (user_id, seller_id, prod_reg_date, prod_id, trade_stats, 구매검토 한정 부분 unique)를 없앤다. 정의서에 없는 우리가 만든 인덱스지만 제약을 바꾸는 일이라 **`db/` 브랜치로 따로** 올리고 승인받는다. 이전 배포와 호환(제약을 푸는 방향이라 무중단 OK). `insertReviewIfAbsent`(`on conflict do nothing`)는 그냥 insert 로.
- **장바구니 → 구매·견적 전환**: 지금은 매물로 그 줄을 찾는다(`cartRowOf`). 줄이 여럿이면 어느 줄인지 모르므로 **요청에 장바구니 거래ID 를 싣는다.** 장바구니 화면에서 누르면 그 줄이 전환되고, 검색·상세에서 직접 구매·견적하면 장바구니 줄은 건드리지 않고 새로 만든다.
- **프론트 선택 키**: 장바구니 표의 선택·기본값 지도(`cartDefaults`)가 매물 키로 되어 있다 → 거래ID 키로. 같은 매물이 여러 줄이면 [비교]는 같은 매물을 두 번 못 비교하니 막거나 한 번으로 센다(구현 때 정함 — 가정 7).
- **100개 상한**은 줄 수로 센다(그대로).
- 장바구니 안 보이던 "이미 담겨 있어요" 안내는 사라진다.

### 가정 (틀리면 말해 달라)
1. **장바구니는 재고가 모자라면 담기 실패.** 지금은 모자라도 담지만, 묶으려면 수량이 있어야 해서 "재고가 부족해요"로 막는다(견적·구매요청과 같은 문구).
2. 장바구니 화면에 "담은 지 1시간 뒤 자동으로 빠져요" 안내 한 줄과 담은 시각 기준 남은 시간(분)을 보인다.
3. 재고 0인데 판매완료가 아닌 매물: 검색 표 수량 칸은 `0`, 거래상태 "거래 중" 그대로(필터 "거래 중"에도 보임). [구매]·[견적]은 "재고가 부족해요"로 막힌다. 새 배지는 만들지 않는다.
4. 수락된 견적 취소 메일은 기존 견적 취소 메일을 재사용한다(새 메일 종류 안 만듦).
5. **이미 있는 개발 데이터**: 수락된 견적·장바구니 행은 묶인 재고가 없는 옛 상태다. 개발 DB 뿐이라 이행 코드는 만들지 않는다. 옛 수락 건에서 [구매]하면 수량이 안 묶여 있어 재고 부족으로 실패할 수 있다 — 개발 데이터는 취소하고 다시 한다.
6. 판매자가 매물 재고·수량을 수정하는 경우: 지금도 구매요청이 깎아 둔 재고 위에 수정할 수 있다. 묶인 수량과의 정합은 이번에 안 건드린다(감수).

7. 같은 매물이 여러 줄인 장바구니에서 [비교]: 같은 소분류 2~4개 규칙에서 같은 매물은 한 번만 센다(중복 줄은 하나로).

### 다른 영역 영향
- API: 새 엔드포인트 없음. 견적 수락 응답·구매·취소 동작이 바뀜(수락된 견적 취소 허용, 수락 때 재고 부족 409 `TRADE_OUT_OF_STOCK`, 장바구니 담기 재고 부족 409). `bruno/trades` 요청 설명 갱신.
- DB: 스키마 변경 없음(마이그레이션 없음).
- 화면: 거래 목록 수락된 견적 줄 [구매]+[취소], 구매 모달(견적에서 열면 수량 고정), 장바구니 안내.
- 메일: 수락/구매 취소 메일 본문의 "단가 변경" 문구 확인.
- 문서: decisions.md(뒤집는 결정: 2026-10-21 견적 수락이 단가를 내림 / 장바구니 재고 안 봄 / 재고 0 즉시 판매완료), security.md(해당 없음), design.md(장바구니 안내·수락 줄 버튼).
