# 정렬 — 검색·판매·거래이력·활동내역 — 계획

## 설계

### 왜
사용자 지적(2026-10-30): 정렬이 거래이력·활동내역 요청·구매에만(칩) 있고 검색 결과·판매 탭엔 없다.
쇼핑 사이트 관례(쿠팡·네이버쇼핑·다나와: 결과 위 "낮은가격순 · 높은가격순 …" 한 줄)를 보여 주고 사용자가 "글자 탭 한 줄"로 정했다.

### 모양 (구현 중 변경 — 사용자 지시 "글자로 하면 작고 몇 개 못한다, 필터식으로")
- 글자 탭으로 만들어 본 뒤 칩으로 바꿨다: 칩 줄 끝 [정렬 ▾] 칩, 고르면 바로·1페이지로. 거래 쪽은 원래 칩 그대로.
- 정렬도 칩 하나라 걸린 개수에 세고 [필터 초기화]가 같이 되돌린다. 주소에 기본값(최신순)은 싣지 않는다.

### 정렬 항목
- 검색 결과·판매 탭(매물): 최신순(기본) · 낮은가격순 · 높은가격순 · 납기빠른순 (사용자 "진짜 필요한 것만" — 재고많은순 뺌)
  - 가격 = 단가(`salesUnitPrice`), 납기 = `deliveryDate`.
  - 같은 값이면 최신 등록순(`regDate desc, userId desc`)으로 끝을 맞춘다.
- 거래이력·활동내역 요청·구매(거래): 최신순 · 금액높은순 · 금액낮은순 (오래된순은 화면에서 뺌). 백엔드 변경 없음.

### 백엔드 (매물 검색만)
- `GET /api/v1/listings` 에 `sort` = `latest`(기본) | `priceAsc` | `priceDesc` | `deliveryAsc`. 그 밖은 400 `fields.sort`.
- 최신순은 지금 그대로(커서·페이지 둘 다). 최신순이 아닌 정렬은 `page` 가 있어야 한다(없으면 400 `fields.sort`) — 거래 목록과 같은 규칙. 프론트는 늘 `page` 를 보낸다.
- 페이지 번호 방식 그대로: `findKeys` 가 정렬 열 + `regDate, userId` 를 그 순서로 전부 읽고 `PageKeys` 로 그 페이지 키만 잘라, 그 키의 매물만 읽어 자바에서 키 순서로 맞춘다(offset 아님 — 거래 목록과 같은 방식).
- DB·인덱스 변경 없음.

### 다른 영역 영향
- 검색 API: 파라미터 추가만. 기존 요청은 최신순 그대로.
- 홈 검색창·`SearchForm` 은 다시 검색해도 정렬을 hidden 으로 유지(필터와 같이).
- 거래 쪽: 칩 그대로, 선택지만 3개로. 주소·API 같음.
- 장바구니·비교는 이번 범위 밖.

### 가정 (틀리면 말해 달라)
- 검색·판매 정렬은 4개로 줄였다 (사용자 "진짜 필요한 것만").
- 브랜치는 PR #103(`feat/trade-search-field`) 위에서 딴다 — 같은 파일(`DetailFilter`·`historyFilter`)을 고쳐 충돌을 피하려고. #103 이 먼저 머지돼야 한다.

## 작업

1. 백엔드
   - `ListingSearchCondition` 에 `sort` + `@Pattern`, 서비스에서 "최신순 아니면 page 필수" 검사.
   - `ListingSearchRepository.findKeys` 정렬별 `order by`(+ 정렬 열을 키에 포함), 페이지 키로 매물 읽기(`findByKeys`) 추가. `ListingService.search` 가 최신순이 아니면 그 경로.
   - 테스트(검색 API 테스트): 정렬 4종 순서, 같은 값이면 최신 먼저, 2페이지로 이어짐, 틀린 sort 400, page 없이 정렬 400, 내 판매(mine)에서도 동작.
   - `bruno/listings/list.bru` 에 `sort`.
2. 프론트 (칩으로 바뀐 뒤 실제로 한 것)
   - `lib/search.ts`: `SearchQuery.sort` — 주소 파싱(틀린 값은 latest)·주소 만들기(기본값 생략)·API 파라미터. 다시 검색해도 남고, 필터 초기화는 최신순으로.
   - 검색 칩 정의(`searchFilterFields`) 끝에 정렬 select 칩, 폼 스키마(`searchFilterSchema`)에 `sort`.
   - 거래 쪽 정렬 칩 선택지를 최신·금액높은·금액낮은 순으로.
   - 문구 `messages/search.ts`(정렬 이름), 거래 쪽은 기존 `my.history.filter.sorts`.
   - 단위 테스트: `search.ts`·`searchFilter`·historyFilter 갱신. E2E `flow.spec.ts` 검색 단계에 정렬 칩.
3. 문서: `docs/security.md` 매물 검색 `sort`, `docs/decisions.md`, `docs/design.md`.
4. 확인: `./gradlew check`, `pnpm typecheck && pnpm lint && pnpm test`, E2E `flow.spec.ts`·`purchase.spec.ts`.
