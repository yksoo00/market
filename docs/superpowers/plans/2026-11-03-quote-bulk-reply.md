# 받은 견적요청 한꺼번에 처리 (2026-11-03)

## 설계

사용자 지시: 요청 탭에서 받은 견적요청을 한 모달에 모아 [모두 수락]·[모두 거절]로 한 번에 처리하고, 그 안에서 건별 [수락]·[거절]도 쓴다.
여러 건 구매·여러 건 견적 요청 모달과 같은 모양이다. 대화로 정한 규칙:

- 모달은 체크한 건이 아니라 **내가 받은 모든 견적요청**(상태 견적요청)을 담는다. 버튼 이름은 [모든 견적요청 보기].
- **상한 30건**, 오래된 요청부터. 넘으면 모달 위에 "견적요청 N건 중 오래된 30건을 보여 줘요. 처리하고 다시 열면 나머지가 나와요."
- **같은 매물끼리 묶어서** 보여 준다. 묶음 머리에 상품명 · 지금 재고 · 요청 합계(재고를 넘으면 빨강).
- 한 구매자는 한 매물에 견적을 하나만 둘 수 있다(기존 규칙) — 한 묶음 안의 줄은 모두 다른 구매자다.
- **[모두 수락]**: 묶음 단위로 판정한다.
  - 합계가 재고 이내면 그 묶음을 전부 수락한다(재고 묶기 + 상태 변경 + 메일, 기존 수락과 같다).
  - 합계가 재고를 넘으면 **그 묶음은 통째로 실패**한다. 서버가 누구를 먼저 받을지 임의로 고르지 않는다. 사유: "견적 합계 12개가 재고 10개를 넘어요. 아래에서 건별로 골라 수락해 주세요."
  - 다른 묶음에서 성공한 건은 그대로 성공으로 처리하고 표시한다(부분 성공).
- **[모두 거절]**: 재고와 무관하게 전부 거절한다.
- 건별 [수락]·[거절]은 지금 쓰는 단건 API 그대로. 합계가 재고를 넘는 묶음에서도 한 건씩 되는 만큼 수락할 수 있다(앞 건이 재고를 쓰면 뒤 건은 재고 부족 409 — 그 줄에 사유 표시).
- 모달을 연 사이 구매자가 취소했거나 다른 곳에서 이미 처리한 건은 **"이미 처리된 견적"** 사유로 실패에 넣고 목록에서 뺀다.
- 실패는 사유와 함께 남기고 성공은 "수락됨/거절됨"으로 표시한다. 뒤의 요청 탭 목록은 처리 뒤 다시 읽는다.
- 일괄 수락·거절은 누르면 확인 문구를 한 번 띄운다: "견적요청 N건(M개 매물)을 모두 수락할까요?" (수락은 수량이 구매자 몫으로 묶이는 일이라).
- 메일은 건별 그대로(구매자 한 명이 한 매물에 하나라 같은 매물 메일이 여러 통 가지 않는다).

### API
- `GET /api/v1/trades/quote-requests` → `{ items, total }`. 판매자(나)가 받은 견적요청 상태 거래를 오래된 순으로 30건, `total` = 전체 건수. 항목: tradeId, regDate(매물), prodName, 구매자 닉네임, orderQuantity, salesUnitPrice, orderUnitPrice, amount, reqDeliDate, remarks, **stockQuantity**(지금 재고).
- `POST /api/v1/trades/quote-requests/reply` `{ tradeIds: 1~30개, decision: "accept" | "reject" }` → 200 `{ results: [{ tradeId, ok, code?, message?, tradeStats? }] }`. 한 건이 틀려도 전체가 실패하지 않는다 — 건별 결과.
  - 매물 묶음마다 **자기 트랜잭션**(실패한 묶음이 성공한 묶음을 되돌리지 않는다). 묶음 안에서는 매물을 `lockForTrade`(배타)로 잠그고 합계·재고를 판정한 뒤 처리한다. 여러 묶음은 (판매자·등록일시) 순으로 처리해 교착하지 않게 한다.
  - 실패 코드는 기존 코드 재사용: 이미 처리·없음 `TRADE_NOT_PENDING`, 내 견적이 아님 `TRADE_NOT_FOUND`(남의 거래 존재를 흘리지 않음), 거래완료 `LISTING_COMPLETED`, 재고 부족 `TRADE_OUT_OF_STOCK`(합계 초과 문구는 서버가 만들어 `message` 로).
  - tradeIds 는 같은 값 중복 제거, 31개 이상은 400.
- 두 API 모두 판매자 본인 것만. 본문의 userId 사용 없음.

### 화면
- 요청 탭(판매자) 목록 위에 [모든 견적요청 보기] 버튼. 누르면 `QuoteRequestsDialog`가 `quote-requests` 를 읽어 매물 묶음으로 보여 준다.
- 모달: 위에 안내 줄(N건 중 30건 / 모두 처리한 뒤 다시 열기), [모두 수락]·[모두 거절]. 묶음 머리 = 상품명 · 재고 · 요청 합계. 줄 = 구매자 · 수량 · 희망단가(등록단가 대비) · 납품희망일 · 요청사항 · [수락][거절].
- 결과: 성공 줄은 회색 + "수락됨/거절됨", 실패 줄은 빨간 사유 + 버튼 유지, 이미 처리된 줄은 사라진다. 모든 줄이 끝나면 "모두 처리했어요" 빈 상태.
- 로딩·빈 상태("받은 견적요청이 없어요")·오류(재시도) 상태 포함. 처리가 끝날 때마다 요청 탭 목록을 다시 읽고(`onTradeChanged` 신호) 헤더 숫자 같은 건 이미 있는 신호를 따른다.
- 새 화면(page)은 없다 — 모달만. 화면 표(`tileScreens`) 등록 없음. 칸 체크리스트: 모달·팝업이 3분할 오른쪽 아래 칸(640×330)에서 잘리지 않는지 — 모달은 창 가운데로 뜨는 기존 방식(2026-11-02 모달 전체화면)을 그대로 쓰고 안에서 스크롤한다.
- 문구는 `messages/trade.ts` 에 모은다.

### 영향 검토
- 견적요청 수락·거절의 **정책은 안 바뀐다**(수락 = 수량 묶기, 거절 = 상태만). 새 건 처리 길이 하나 더 생길 뿐이다.
- 재고 판정은 묶음 합계(사전) + 건별 조건부 UPDATE(최종) 두 겹이다. 사전 합계가 맞아도 그 사이 다른 구매가 재고를 가져가면 그 건만 `TRADE_OUT_OF_STOCK` 으로 실패한다(부분 성공).
- DB 스키마 변경 없음. 새 라이브러리 없음. 단건 accept/reject API·화면 동작 변화 없음.
