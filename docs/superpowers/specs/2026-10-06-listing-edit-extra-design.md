# 매물 수정·판매정보 추가등록 설계

날짜: 2026-10-06 · 상태: 검토 대기

## 목표

판매자가 올린 매물을 두 가지 화면으로 보완한다.

- **수정**: 이미 입력한 기존 칸(가격·수량·상태·납기·설명·사진·데이터시트)을 고친다.
- **판매정보 추가등록**: 등록 뒤 나중에 보증기간·불량지원·대체품·테스트리포트·정품인증서를 보탠다.

두 기능은 사용자 결정으로 화면을 따로 둔다 (한 화면 + 구역 방식은 고르지 않았다). 홈의 "판매정보 추가등록" 아이콘은 수정 폼이 아니라 추가등록 화면으로 간다.

## 이미 있는 것 (바꾸지 않는다)

- 백엔드 `PATCH /api/v1/listings/{userId}/{regDate}`: 본인만, null 필드는 미수정, 파일 칸 `""`는 비우기, 이 매물에 이미 저장된 업로드 키는 다시 올리지 않아도 통과, 납기일은 저장값 그대로면 지난 날짜여도 통과. 요청 DTO는 `ListingUpdateRequest`.
- 업로드: 2단계(`POST /api/v1/uploads` → 키). 용도별 형식은 업로드 정책 그대로 (대체품 pdf/jpg/png, 테스트리포트·인증서·데이터시트 pdf — security.md "파일 업로드").
- 등록 폼의 칸 컴포넌트·검증 조각(`lib/validation/listing.ts`), 상품상태 드롭다운 `PROD_STATES`.
- 상세 화면의 [수정] 버튼은 지금 "준비 중" 안내만 띄운다.

## 화면

| 경로 | 역할 |
|---|---|
| `/listings/{userId}/{regDate}/edit` | 수정 |
| `/listings/extra` | 추가등록 대상 매물 고르기 (홈 아이콘이 여기로) |
| `/listings/{userId}/{regDate}/extra` | 추가등록 입력 |

세 화면 모두 로그인 필요 (`RequireLogin`). 남의 매물이면 서버가 403이고 화면은 "내 매물만 수정할 수 있어요"를 보여 준다. 상세 화면의 내 매물 버튼은 [수정]·[판매정보 추가]·[삭제].

### 수정 화면

- 매물 상세를 조회해 폼에 채운다. 로딩은 스켈레톤, 조회 실패는 "불러오지 못했어요" + [다시 시도], 없으면 "매물을 찾을 수 없음".
- 편집 칸: 상품상태, 단가, 판매수량, 재고수량, 최소주문량, 주문단위, 납기일, 설명, 사진, 데이터시트.
- 상품마스터 칸(카테고리·상품명·제조사·상품번호·제조일·사양)은 서버가 수정을 받지 않으므로 위에 읽기 전용으로 보여 준다. 거래종류는 "등록" 고정이라 칸이 없다.
- `ListingForm`은 등록 전용 전제(상품마스터 칸·`emptyListingForm`)가 섞여 있다. 수정용 `ListingEditForm`을 따로 두고, 개별 칸 컴포넌트(`FormField`·`ProdStateField`·`NumberField`·`DescriptionField`)와 검증 조각은 공유한다.
- 옛 상품상태 값(`신품대비 70%` 같은 이전 형식)은 가까운 구간(70~79%)으로 바꿔 채운다. 매핑은 `lib/listingEdit.ts`의 순수 함수. 구간에 안 맞는 값(예: `양호`)은 "선택하세요"로 두고 사용자가 고르게 한다.
- 사진·데이터시트 업로더는 지금 빈 상태에서 시작한다 (코드 TODO 두 곳). 기존 키로 초기화하도록 고친다. 기존 사진 미리보기는 `fileUrl()`, 기존 데이터시트는 파일 이름 대신 "등록된 데이터시트"로 표시한다.
- 저장은 **바뀐 칸만** PATCH로 보낸다 (`dirtyFields`). 하나도 안 바뀌면 [저장] 비활성. 등록 폼에서는 재고·최소주문량·주문단위를 비우면 서버 기본값이 들어가지만, 수정에서는 이미 값이 있는 칸이라 비울 수 없게 필수로 둔다.
- 납기일을 비우면 `""`, 저장값 그대로면 서버가 지난 날짜도 통과시킨다.
- 성공 → 상세로 이동. 서버 필드 오류는 해당 칸에 붙인다. 제출 중 중복 방지, 업로드 중 [저장] 비활성, 업로드 실패 시 다시 시도는 등록 폼과 같다.

### 추가등록 — 매물 고르기 (`/listings/extra`)

- 내 매물 목록(`GET /api/v1/listings/mine`) + [더 보기](커서). 한 줄: 상품명 · 상품번호 · 등록일 · "보증·서류 N/5". 행을 누르면 입력 화면.
- 빈 상태: "등록한 매물이 없어요" + [매물 등록하기]. 오류·429는 검색 결과와 같은 문구와 [다시 시도].

### 추가등록 — 입력 (`/listings/{userId}/{regDate}/extra`)

- 칸: 보증기간(없음·1·3·6·12·24·36개월 드롭다운), 불량지원(없음·대체·환불 드롭다운), 대체품, 테스트리포트, 정품인증서(파일, 형식은 업로드 정책).
- 이미 채운 값은 미리 채워 보여 주고, 바꾸거나 [삭제]로 비운다 (파일 칸 `""`).
- 바뀐 칸만 PATCH. 수정 화면과 같은 저장·업로드 처리.
- 보증기간과 불량지원이 짝이 안 맞아도(한쪽만 채움) 강제하지 않는다 — 서버 규칙에도 없고, 사용자가 안 정했다.

## 백엔드

신규는 하나다.

- `GET /api/v1/listings/mine?cursor=` — 로그인 필요(비로그인 401), 요청자 본인의 매물만, 최신순, 커서 페이지 20개 (`{ items, nextCursor }`). 검색 결과 항목 형식에 `extraFilled`(0~5: 보증기간·불량지원·대체품·테스트리포트·정품인증서 중 채운 개수)를 더한다. 개인정보는 응답에 없다. 요청자 id는 `@AuthenticationPrincipal`에서만 가져온다.
- `ListingUpdateRequest.warrantyPeriod`에 **허용 일수 목록** 검증을 더한다: 0 · 30 · 90 · 180 · 360 · 720 · 1080. 프론트 개월 드롭다운(0·1·3·6·12·24·36개월 × 30일, 12개월=360일)과 같은 목록이다. 기존 서버 규칙(0~36,500)은 자유 숫자라 같은 값이 흩어진다는 점에서 상품상태 구간과 같은 이유로 바꾼다. 옛 값(예: 365일)이 DB에 있으면 수정 화면에서 가까운 구간으로 보여 준다.
- 쓰기 API는 기존 PATCH를 그대로 쓰고 rate limit도 그대로다 (`listing:update`, 입력 검증 실패는 세지 않음). `/mine`은 읽기라 별도 한도를 두지 않는다 (로그인 사용자만, 페이지 크기 고정).

## 문서·Bruno

- security.md: 보증 일수 허용 목록, `/mine` 접근 규칙·응답 항목.
- design.md: 세 화면 규격 (칸 배치는 매물 등록 폼과 같은 라벨 왼쪽).
- decisions.md: 화면 분리, 보증 개월 드롭다운, 옛 값 매핑.

## 테스트

- 백엔드: `/mine` 정상(내 것만·최신순·커서·`extraFilled`), 비로그인 401, 다른 사용자 매물 제외, 보증 일수 목록 밖 값 400·목록 안 값 통과.
- 프론트(Vitest): 옛 상태 값 → 구간 매핑, 바뀐 칸만 뽑는 함수, 개월↔일수 변환, 채움 개수 표시.
- 화면 동작(업로더 초기화·dirty 계산·버튼 활성)은 이번엔 브라우저 수동 확인. Playwright 흐름 테스트는 별도 작업.
