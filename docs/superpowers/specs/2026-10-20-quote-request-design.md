# 견적요청: 구매자 희망단가 → 판매자 회신(수락=매물 단가 변경 / 거절) → 구매자가 따로 구매

> 2026-10-20. 사용자 지시(대화)로 정함. 장바구니·비교용(`구매검토`)은 다음 작업 — 이번엔 값만 정의서에 맞춰 둔다.

## 목적

검색 결과·상세의 [견적 요청]을 켠다. 구매자가 매물에 희망단가를 보내면 판매자가 수락(그 단가로 매물 단가를 바꿈)하거나 거절한다.
결과는 메일로 알리고, 구매자는 바뀐 매물을 기존 [구매]로 산다. decisions.md 미정 "견적 흐름"을 닫는다(연락처는 공개하지 않고 메일로만 잇는다).

## 거래종류·거래상태 (정의서 `TRADE_TYPE`·`TRADE_STATS`)

두 칸의 역할을 나눈다 (사용자 결정).

- **TRADE_TYPE = 무슨 기록인가.** 만들 때 정하고 바뀌지 않는다: `구매검토` · `견적조정` · `거래`
- **TRADE_STATS = 지금 어디까지 왔나.** 앞으로만 바뀐다: `장바구니` · `비교용` · `견적요청` · `견적회신` · `구매요청` · `구매확정`

| TRADE_TYPE | TRADE_STATS 흐름 | 비고 |
|---|---|---|
| 구매검토 | `장바구니` / `비교용` | 다음 작업 (이번엔 쓰지 않음) |
| 견적조정 | `견적요청` → `견적회신` | 수락·거절 모두 `견적회신`. 어느 쪽인지는 메일로만 알린다 (사용자 결정) |
| 거래 | `구매요청` → `구매확정` | 지금 [구매] |

- 정의서 값 중 `요청중`(TYPE)은 쓰는 곳이 없어 쓰지 않는다.
- `견적회신`은 정의서에 없는 값 — 사용자 결정으로 추가.
- 취소는 값으로 남기지 않는다. 행을 지우고 상대에게 메일 (사용자 결정, 견적·거래 모두).
- 지금 거래가 쓰는 TYPE `구매요청`/`구매확정`/`구매취소`와 STATS `취소`는 없어진다 → 아래 "기존 데이터".

## 흐름

| 동작 | 누가 | 조건 | DB | 재고 | 메일 |
|---|---|---|---|---|---|
| 견적 요청 | 구매자 | 남의 매물, 거래완료 아님, 같은 매물에 내 `견적요청`이 없음 | 행 생성 `견적조정`/`견적요청` | 그대로 | 판매자 |
| 수락 | 그 매물 판매자 | `견적요청` | 매물 `sales_unit_price` = 희망단가, 행 → `견적회신` | 그대로 | 구매자 |
| 거절 | 그 매물 판매자 | `견적요청` | 행 → `견적회신` | 그대로 | 구매자 |
| 견적 취소 | 구매자 | `견적요청` | 행 삭제 | 그대로 | 판매자 |
| 구매 | 구매자 | 지금 [구매]와 같음 | 행 생성 `거래`/`구매요청` | 줄임 | 판매자 |
| 거래 취소 | 구매자·판매자 | `구매요청` | 행 삭제 | 되돌림 (거래완료였으면 `dt_expire` 지움) | 상대 |
| 거래완료 | 구매자 | `구매요청` | 행 → `구매확정`, HISTORY 1줄 | — | 둘 다 |

- 상태 바꾸기는 지금 확정·취소처럼 조건부 UPDATE/DELETE(`where trade_stats = …`) 행 수로 판정 — 수락을 두 번 누르거나 수락·거절·취소가 겹쳐도 하나만 성공, 나머지는 409 `TRADE_NOT_PENDING`. 메일도 한 번만.
- 수락: 매물 행을 잠그고(`findForUpdate`) 거래완료면 409 `LISTING_COMPLETED`(단가를 바꿔도 살 수 없다). 수락 때 매물이 이미 희망단가보다 싸면 그대로 둔다(올리지 않음).
- 단가 변경은 그 매물을 보는 모든 구매자에게 적용된다 (매물 단가 자체가 바뀜).
- 견적 행은 회신 뒤에도 남는다 — 구매자 목록에서 "회신 완료"를 보고 그 줄의 [구매]로 산다.

## 칸 쓰는 법 (`trd_trade_info`, 견적조정 행)

| 칸 | 값 |
|---|---|
| `order_unit_price` | 희망단가 (구매자 입력) |
| `order_quantity` | 수량 (구매자 입력) — 수락해도 매물 수량은 바꾸지 않는다(참고용) |
| `remarks` | 비고 |
| `req_deli_date` | **null** — 희망납품일은 받지 않는다 (사용자 결정). 지금 NOT NULL → nullable 마이그레이션 |
| `sales_unit_price`·`prod_id`·`prod_state`·`stock_quantity`·`min_order_quantity`·`order_unit`·`prov_date` | 요청 때 매물에서 복사 (지금 구매와 같음) |
| `trade_id` | 지금 규칙 그대로 (`yyMMddHH`+순번) |

## 검증 (프론트 zod + 백엔드 같은 규칙, security.md 에 추가)

- 한 번에 1 ~ 20개 매물. 전부 통과해야 저장(하나라도 틀리면 아무것도 안 생김).
- 희망단가: 1 ~ 그 매물의 등록단가(요청 때).
- 수량: 지금 구매와 같은 규칙 — 최소주문량 이상, 주문단위 배수, 재고 이하, 희망단가 × 수량 ≤ 2,147,483,647.
- 비고: 100자 이하.
- 거절 이유: 자기 매물 403 `TRADE_OWN_LISTING`, 거래완료 409 `LISTING_COMPLETED`, 같은 매물에 내 `견적요청`이 이미 있음 409 `QUOTE_ALREADY_REQUESTED`(새 코드).
- 오류 위치: `fields["items[2].orderUnitPrice"]` 처럼 행 번호 + 칸.

## API

| 메서드·경로 | 누가 | 하는 일 |
|---|---|---|
| `POST /api/v1/trades/quotes` `{ items: [{ sellerId, regDate, orderUnitPrice, orderQuantity, remarks }] }` | 로그인 | 견적 요청 N건. `Idempotency-Key` 받음(scope `quote-create`) |
| `POST /api/v1/trades/{tradeId}/accept` | 판매자 | 수락 |
| `POST /api/v1/trades/{tradeId}/reject` | 판매자 | 거절 |
| `POST /api/v1/trades/{tradeId}/cancel` | 견적: 구매자 / 거래: 양쪽 | 행 삭제 (지금 cancel 을 바꿈) |
| `GET /api/v1/trades?role=buyer\|seller` | 로그인 | 지금 목록에 견적조정 행 포함. 응답에 `tradeType`(`quote`·`purchase`)·`salesUnitPrice`(등록단가) 추가, `tradeStats` 값은 `quoteRequested`·`quoteReplied`·`requested`·`confirmed` |
| `GET /api/v1/trades/pending-counts` | 판매자 | `견적요청` + `구매요청` 건수 (판매자가 처리할 것) |

- 남의 거래는 지금처럼 403/404. 응답에 이메일·전화 없음 (메일 주소는 서버 안에서만 쓴다).
- Bruno: `trades/quote-create`·`accept`·`reject` 추가, `cancel` 갱신.

## 메일 (하이웍스 SMTP)

- 의존성 `spring-boot-starter-mail` 추가 (사용자 확인 2026-10-20).
- `common/mail`: 보내는 쪽 인터페이스 하나. `.env` 의 `MAIL_HOST`·`MAIL_PORT`·`MAIL_USERNAME`·`MAIL_PASSWORD`·`MAIL_FROM` 이 있으면 SMTP, 없으면 로그만 남긴다(로컬·테스트). `.env.example` 엔 키 이름만.
- 트랜잭션 커밋 뒤에 보낸다(`@TransactionalEventListener(AFTER_COMMIT)`) — 롤백된 요청에 메일이 가지 않게. 실패해도 요청은 그대로 두고 WARN 로그(거래ID·받는 사용자 uid 만, 메일 주소 없음).
- 받는 주소: `trd_user_info.email`. 비어 있으면 건너뛰고 로그.
- 본문: 상품명, 등록단가·희망단가(견적) 또는 단가·수량(거래), 상대 닉네임, 해당 화면 링크(`APP_URL` 기준). 문구는 백엔드 `mail` 템플릿 한 곳.
- 7가지: 견적 요청(→판매자), 수락·거절(→구매자, 결과 구분), 견적 취소(→판매자), 구매요청(→판매자), 거래 취소(→상대), 거래완료(→둘 다).

## 화면

- **검색 결과** [견적 요청]: 체크 1~20개 → 견적 모달. 매물마다 한 줄: 상품명·등록단가·재고·최소주문량·주문단위 + 입력 희망단가·수량·비고. 요청할 수 없는 매물(내 매물·거래완료·이미 요청함)은 이유를 보이고 보내지 않는다. 21개 이상이면 안내.
- **상세** [견적 요청]: 같은 모달, 한 줄. 비로그인은 지금 [구매]처럼 로그인으로.
- **내 구매목록** `/my/purchases`: 견적 줄 — 상태 견적요청/회신 완료, 등록단가·희망단가. `견적요청` 줄 [취소], `견적회신` 줄 [구매](지금 구매 모달이 그 매물로).
- **받은 구매요청** `/my/sales`: 견적 줄 — 구매자 닉네임·희망단가·수량·비고, `견적요청` 줄 [수락]·[거절](확인 창).
- **내 판매글** "구매요청 N건": 견적요청 포함.
- **홈 아이콘·앱 메뉴**: "상품검색·견적 요청" → `/search`, "견적 확인" → `/my/purchases` (지금 임시 경로 교체).
- 새 page 없음. 모달은 칸 체크리스트대로 3분할 칸 크기(960×500, 640×330)에서 확인.
- 거래 취소 후 행이 사라지므로 목록의 "취소" 상태 표시·필터는 없앤다.
